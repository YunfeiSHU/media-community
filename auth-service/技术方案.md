# Auth-Service技术方案

## 文档信息

| 项目 | 内容 |
| --- | --- |
| 服务名称 | `auth-service`，监听 `8002` |
| 技术基线 | Java 17、Spring Boot 3.3.5、MyBatis 3.0.3、MySQL 8、Redis 7、Dubbo 3（注册中心 Nacos） |
| 核心能力 | 手机号/邮箱注册与登录、验证码、双令牌（access + refresh）、Refresh Token Rotation、注销黑名单、管理员强制下线、登录 IP 限流 |
| 接口与错误码 | 完整清单与错误码总表见 [../README.md](../README.md) §5.3、§5.4，本文不重复 |

## 总体设计

### 系统边界

`auth-service` 只负责账号身份、凭据校验和 Token 生命周期，不承载用户资料、权限模型或业务资源。账号数据写入本服务 MySQL 的 `account` 表；用户资料由 `user-service` 通过 Dubbo 管理，两表只共用 `uid` 关联。验证码、登录 Session、JWT 黑名单写入 Redis。

```text
Client
  |
  v
AuthController  ---- Bean Validation / 统一响应 / 登录 IP 限流
  |
  v
AuthService / VerificationService / SessionService
  |                    |                        |
  v                    v                        v
AccountRepository   StringRedisTemplate      JwtTokenService（HMAC-SHA256）
MyBatis -> account  验证码 / Session / 黑名单        |
  |                                                |
  +-- PasswordEncoder（BCrypt）                     |
  +-- NotificationProvider（短信/邮件，当前为打日志的桩实现）
  +-- UserServiceClient --Dubbo(Nacos)--> user-service :20880
```

### 分层职责

| 层级 | 主要职责 |
| --- | --- |
| Controller | 接收请求、Bean Validation、登录限流前置检查、封装统一响应 |
| Service | 注册登录编排、验证码管理、JWT 生成解析、Session 轮换、注销黑名单 |
| Repository | MyBatis 注解 SQL，只读写 `account` 表 |
| Provider | 隔离短信/邮件发送渠道，当前为桩实现，便于替换真实供应商 |
| MySQL | 保存登录凭证、密码摘要、状态和审计时间，不保存用户资料 |
| Redis | 验证码、发送冷却、Refresh Session（Hash）、Access Token 黑名单、登录限流计数 |

### 核心设计原则

1. 密码只保存 BCrypt 摘要；Refresh Token 在 Redis 只保存 SHA-256 摘要，不保存明文。
2. JWT 用不可变业务标识 `uid` 作为 `sub`，不暴露 `account` 自增主键 `id`。
3. 手机号、邮箱、`uid` 各建唯一索引，并发注册由数据库做最终防线。
4. Refresh Token 每次刷新都轮换，旧 Session 删除与新 Session 创建由一段 Redis Lua 原子完成。
5. 验证码、Session、黑名单都带 TTL，不留无期限数据。

### 跨服务用户创建

注册由 auth-service 编排、user-service 落资料，`account` 与 `user` 通过 `uid` 关联（`account` 表**没有** `user_id` 列）。

```text
校验并消费验证码 -> 归一化联系方式 -> 查 account 是否已存在
       |
       v
Dubbo createUser(new CreateUserCommand())   // 空命令，只让 user-service 生成 uid + 默认资料
       |
       v
拿到 uid 后写入 account（uid/phone 或 email/password_hash/status/timestamps）
```

- 命令对象为空是因为注册阶段只有登录凭证，昵称/头像等资料由用户之后调 `PUT /api/v1/users/me` 补充。
- `@DubboReference(check = false, timeout = 3000)`：启动不校验提供者在线，允许用户中心暂时不可用；调用异常在注册链路上转为 `50000`。
- 注册中心为 Nacos（`dubbo.registry.address`，默认 `nacos://localhost:8848`），可用 `DUBBO_REGISTRY_ADDRESS` 覆盖；user-service 默认监听 `20880`，直连排查时可临时给 `@DubboReference` 加 `url = "dubbo://127.0.0.1:20881"`。

已知取舍（当前实现未做补偿）：

| 问题 | 后果 |
| --- | --- |
| 没有 `registrationId` 幂等键，`createUser` 每次调用都会新建资料 | RPC 超时重试可能产生孤儿 `user` 行 |
| Dubbo 调用与 Redis 删除都在 `@Transactional` 内 | 事务回滚不会撤销已删的验证码和已建的用户资料 |
| `user` 建成功、`account` 写失败 | 留下无 `account` 的孤儿用户，需人工或后续对账清理 |

## 公共约定

### 账号规则

- 新用户只能用手机号或邮箱注册，`username` 在当前链路始终为 `NULL`（保留列与 `uk_username` 唯一索引，为将来的用户名登录预留；MySQL/H2 允许多个 NULL）。
- 一个新用户只绑定一种身份：手机号注册时 `phone` 有值、`email` 为 `NULL`，邮箱注册相反。
- 邮箱统一转小写后写入和查询；手机号按中国大陆 `^1[3-9]\d{9}$` 校验。
- 密码长度 8~20 个字符，验证码固定 6 位数字。

### 统一响应与错误码

```json
{ "code": 0, "message": "success", "data": { } }
```

`code = 0` 为成功。完整错误码表见 [../README.md](../README.md) §5.3，本节只列 auth-service 实际产出的码：

| HTTP | code | 触发场景 |
| --- | --- | --- |
| 200 | `0` | 成功 |
| 400 | `40001` | 参数校验失败（如 `phone 格式不正确`、`无法识别客户端 IP`） |
| 400 | `40000` | 凭据错误、联系方式已注册、验证码无效或已过期 |
| 401 | `40101` | 未认证（`Access Token 无效`、Refresh Token 无效、缺少身份头） |
| 403 | `40301` | 无权限（强制下线调用者不是 `ADMIN`） |
| 429 | `42901` | 验证码 60 秒冷却内重复发送、登录 IP 限流超限 |
| 500 | `50000` | 创建用户档案失败等内部错误 |

错误码前三位与 HTTP 状态码对齐（`40001` → 400），由 `ErrorCode` 枚举统一映射。

### 数据标准化与时间约定

- 手机号去首尾空格后校验，仅支持 `1[3-9]` 开头 11 位。
- 联系方式的归一化**看目标是否含 `@`，不看请求里的 `type`**：底层 SQL 是 `WHERE phone = ? OR email = ?`，两列都参与匹配；若按 `type` 判断，`type=phone` 却传大写邮箱时不会转小写，就查不到已注册账号（表现为登录报“用户名或密码错误”）。
- 服务端时间字段以 ISO-8601 字符串写入 Redis；MySQL 审计字段用 `DATETIME`。
- Token 有效期与 Redis TTL 均以秒为单位，服务端是有效期的唯一可信来源。

### 身份传递

下游服务不解析 JWT，只信任网关先清后写的 `X-User-Id`（= JWT `sub`）与 `X-User-Role`（= JWT `role` claim）。请求体或查询参数里自报的 uid/角色一律不采信。`force-logout?uid=` 的 `uid` 是**操作目标**，不是调用者身份。直连 `8002` 绕过网关时伪造这两个头仍可冒充身份，生产环境须在网络层禁止直连。auth-service 自己只在 `logout` / `force-logout` 里解析 JWT（取 `jti` 与 `exp` 写黑名单），不做业务鉴权。

### 关键配置项

`SERVER_PORT`（`8002`）、`auth.jwt.secret` / `JWT_SECRET`（历史名 `AUTH_JWT_SECRET`，≥32 字节，须与网关一致）、`auth.jwt.access-token-ttl-seconds`（`1800`）、`auth.jwt.refresh-token-ttl-seconds`（`604800`）、`auth.verification.expose-code`（`true`）、`auth.login-rate-limit.max-attempts`（`5`）、`auth.login-rate-limit.window-seconds`（`60`）、`server.forward-headers-strategy`（`framework`，限流取真实 IP 依赖）、`SPRING_SQL_INIT_MODE`（`always`）、`DUBBO_REGISTRY_ADDRESS`（`nacos://localhost:8848`）、`DUBBO_TIMEOUT`（`3000` 毫秒）。

## 1. 需求一：发送手机或邮箱验证码

接口 `POST /api/v1/auth/verification/send`。

| 字段 | 必填 | 取值 | 说明 |
| --- | --- | --- | --- |
| `purpose` | 是 | `register`、`login`、`reset_password` | 验证码用途，参与 Redis Key |
| `type` | 是 | `phone`、`email` | 发送渠道，决定 Provider 与格式校验 |
| `target` | 是 | 手机号或邮箱 | 接收目标，去空格；邮箱转小写 |

响应 `data` 为 `{purpose, type, target, code}`。`code` 由 `auth.verification.expose-code` 控制：默认 `true`（学习模式，短信/邮件 Provider 只是打日志的桩，没有真实通道），此时验证码随响应返回；置为 `false` 后 `send()` 返回 `null`，验证码只留在 Redis 与通知通道里。

### 1.1 设计流程

```text
接收 purpose + type + target
              |
              v
按 type 校验并标准化（phone 正则 / email 正则 + 小写）
              |
              v
检查 Redis cooldown Key
       |                 |
      存在               不存在
       |                 |
 返回 42901        生成 6 位验证码
  “验证码获取过于频繁”          |
                        v
                调用 SMS/Email Provider
                   |             |
                发送失败        发送成功
                   |             |
             不写入 Redis    写验证码 Key -> 写 cooldown Key -> 返回
```

### 1.2 Redis 设计

| 数据 | Key | Value | TTL |
| --- | --- | --- | --- |
| 验证码 | `auth:verification:{purpose}:{type}:{target}` | 6 位数字 | 180 秒 |
| 发送冷却 | `auth:verification:{purpose}:{type}:{target}:cooldown` | `1` | 60 秒 |

示例：`auth:verification:register:phone:13800138000`、`...:cooldown`。

- 写入顺序固定为：Provider 发送成功 → 写验证码 Key → 写 cooldown Key。发送失败不写 Redis，否则用户既没收到码又被锁 60 秒。
- 冷却判断是 `hasKey` + 之后 `set`，两步非原子：同一目标的高并发请求可能都通过检查并各发一条验证码。生产环境应改为 `SET NX EX` 或 Lua，本项目未这样做（Lua 只用于网关限流、Refresh Rotation 和弹幕限流）。
- 发送验证码不读写 MySQL；注册重复性由注册流程与唯一索引保证。

## 2. 需求二：手机号注册

接口 `POST /api/v1/auth/register/phone`，请求体 `{phone, code, password}`：`phone` 需匹配 `^1[3-9]\d{9}$`，`code` 为 6 位数字，`password` 8~20 字符。

```text
接收 phone + code + password
             |
             v
Bean Validation（phone 正则 / code 6 位 / password 8~20）
             |
             v
读取 Redis 验证码 Key
       |                  |
  不存在/不匹配          匹配
       |                  |
  40000 验证码无效     删除验证码 Key（一次性）
                            |
                            v
                 查 account 是否已存在该手机号
                     |             |
                    是             否
                     |             |
             40000 已注册    Dubbo createUser 取 uid
                                   |
                                   v
                        BCrypt 加密 -> INSERT account
                                   |
                                   v
                              注册成功
```

### 2.1 MySQL 写入

| 字段 | 写入值 |
| --- | --- |
| `uid` | user-service 返回的业务 uid |
| `username` | `NULL` |
| `phone` | 标准化后的手机号 |
| `email` | `NULL` |
| `password_hash` | BCrypt 摘要（`VARCHAR(100)`） |
| `status` | `1` |
| `created_at` / `updated_at` | 当前时间 |

查重与登录共用一条 SQL（`AccountRepository#findByContact`）：

```sql
SELECT id, uid, username, phone, email, password_hash, status, created_at, updated_at
FROM account WHERE phone = ? OR email = ? LIMIT 1;
```

`phone` 上有 `uk_phone`（`email` 上 `uk_email`）。应用层先查一次只为给出友好提示；并发注册时两次查询可能同时为空，最终由唯一索引拦下，`DuplicateKeyException` 转成 `40000 联系方式已注册`。验证码校验成功后立即删除该 Key，保证一码一用；cooldown Key 不因注册成功删除，按 60 秒自然过期。

## 3. 需求三：邮箱注册

接口 `POST /api/v1/auth/register/email`，请求体 `{email, code, password}`；流程与手机号注册完全一致，只走 email 分支。字段校验对应为邮箱正则 `^[^@\s]+@[^@\s]+\.[^@\s]+$`、6 位验证码、8~20 位密码。

差异只有三点：

| 项 | 手机号注册 | 邮箱注册 |
| --- | --- | --- |
| 标准化 | 去空格 | 去空格 + 转小写（参与 Redis Key、SQL 查询、写入） |
| `account.phone` / `email` | `phone` 有值、`email` 为 `NULL` | `email` 有值、`phone` 为 `NULL` |
| 唯一索引 | `uk_phone` | `uk_email` |

验证码 Key 形如 `auth:verification:register:email:user@example.com`，同样在匹配成功后删除。注册写的是同一张 `account` 表（不是 `user` 表）。

## 4. 需求四：手机号或邮箱登录

接口 `POST /api/v1/auth/login`，请求体 `{type, target, password}`；`type` 为 `phone` 或 `email`，仅声明渠道（查库仍是 `phone = ? OR email = ?`），`target` 含 `@` 时先转小写后再查。

```text
接收 type + target + password
              |
              v
IP 限流前置检查（LoginRateLimitService.checkBeforeLogin）
              |
              v
归一化 target（含 @ 则转小写）
              |
              v
account 按 phone OR email 查询
         |                 |
       不存在              存在
         |                 |
   40000 登录失败      检查 status = 1 且 BCrypt 匹配
                            |          |
                          失败        成功
                            |          |
                      40000 登录失败  生成 jti + Access Token
                                          |
                                          v
                              创建 Redis Session（7 天）
                                          |
                                          v
                      返回 uid / accessToken / refreshToken / 两个 expiresIn
                                          |
                                          v
                              登录成功 -> 清空该 IP 限流计数（见 §8）
```

成功响应：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "uid": "7f1f8c9b5e0a4b8c9f2c1d3e4a5b6c7d",
    "accessToken": "eyJhbGciOiJIUzI1NiJ9...",
    "refreshToken": "7f1f8c9b5e0a4b8c9f2c1d3e4a5b6c7d.session-id.random-secret",
    "accessTokenExpiresIn": 1800,
    "refreshTokenExpiresIn": 604800
  }
}
```

用户不存在、`status != 1`、密码不匹配三种情况返回同一条消息“用户名或密码错误”，不区分原因，避免账号枚举。登录只读 MySQL 不写，另通过 Dubbo `getUser(uid)` 取用户档案里的 `role` 用于签发 JWT（档案缺失时退回 `account.uid` 与 `user` 角色）。

## 5. 需求五：Access Token 与 Refresh Token 生命周期

```text
                         登录
                          │
                          ▼
                    用户身份认证（MySQL + BCrypt）
                          │
                          ▼
                  ┌───────────────┐
                  │ 创建 Session  │
                  │    Redis      │
                  └───────┬───────┘
                          │
              ┌───────────┴───────────┐
              ▼                       ▼
       Access Token             Refresh Token
          JWT 30 分钟             随机串 7 天
              │                       │
              ▼                       ▼
         访问业务 API             调用 /token/refresh
              │                       │
              ▼                       ▼
      网关验签 + 查黑名单        Lua 原子轮换 Session
              │                       │
              ▼                       ▼
         X-User-Id               新 access + 新 refresh
```

| 项 | Access Token | Refresh Token |
| --- | --- | --- |
| 形态 | JWT（HS256，jjwt 签发） | 不透明随机串 `{uid}.{sessionId}.{randomSecret}` |
| 有效期 | `auth.jwt.access-token-ttl-seconds`，默认 `1800`（30 分钟） | `auth.jwt.refresh-token-ttl-seconds`，默认 `604800`（7 天） |
| 服务端存储 | 不存；只存 Redis Session 里的 `jti` 与黑名单 | Redis Session 里只存 SHA-256 摘要 |
| 校验方 | 业务鉴权在 `gateway-service`；auth-service 仅在注销/强制下线时解析它取 `jti` | `auth-service` |
| 失效手段 | `auth:blacklist:{jti}` | 删除 Session（轮换或强制下线） |

两个 TTL 都可用 `AUTH_ACCESS_TOKEN_TTL_SECONDS` / `AUTH_REFRESH_TOKEN_TTL_SECONDS` 覆盖，登录与刷新的响应值取自同一份配置。

### 5.1 登录签发规则

1. 按 `type + target` 查 `account`，用户不存在、`status != 1` 或 BCrypt 校验失败则直接失败，不签发任何 Token。
2. 生成随机 `jti`（UUID）。
3. 用 `uid` 作为 `sub`，写 `iss = auth-service`、`aud = api`、`jti`、`iat`、`exp`。
4. 写 `role` claim：user-service 返回的角色码为 `0` 时写 `ADMIN`，否则写 `user`；网关把该 claim 注入 `X-User-Role`，两侧必须同名（`role`）。
5. 用 `auth.jwt.secret` 做 HMAC-SHA256 签名，密钥不可由客户端传入、不可提交仓库；必须与 `gateway.auth.jwt.secret` 用同一把（历史踩坑：两侧变量名与默认值不同，导致网关验签全 401）。
6. 以同一 `jti` 创建 Redis Session，写入成功后才返回完整响应。

JWT Payload 示例：

```json
{
  "iss": "auth-service",
  "sub": "7f1f8c9b5e0a4b8c9f2c1d3e4a5b6c7d",
  "aud": "api",
  "jti": "jti-100",
  "role": "user",
  "iat": 1726754400,
  "exp": 1726756200
}
```

受保护接口的完整校验（验签、`exp`、`sub`、`jti`、黑名单）在网关完成，auth-service 只通过 `JwtBlacklistService.isBlacklisted(jti)` 暴露查询能力，供后续内部转发场景使用。

### 5.2 刷新接口

`POST /api/v1/auth/token/refresh`，请求体 `{"refreshToken": "{uid}.{sessionId}.{randomSecret}"}`。成功返回与登录同构的新双令牌（`expiresIn` 为 1800 / 604800）；失败返回 `40101 Refresh Token 无效或已过期`。

```text
提交 Refresh Token
        |
        v
SessionService 解析 uid/sessionId（格式不合法在访问 Redis 前就拒绝）
        |
        v
生成新 jti、新 sessionId、新 Refresh Token
        |
        v
Redis Lua 原子校验旧 refreshTokenHash
     |                         |
 不存在/摘要不匹配             匹配
     |                         |
 40101 失败          删除旧 Session + 创建新 Session
                                   |
                                   v
                   用新 jti 生成 Access Token（role 再查一次 user-service）
                                   |
                                   v
                     返回新 access + 新 refresh（TTL 均为 7 天）
```

刷新不校验密码，但会再查一次 user-service 取 `role`，所以用户角色变更在下次刷新时生效。旧 Refresh Token 在轮换成功瞬间失效，无法二次使用。

### 5.3 Redis Session

Key：`auth:session:{uid}:{sessionId}`，Value 为 Hash，TTL 固定 604800 秒。

| 字段 | 说明 |
| --- | --- |
| `uid` | 用户业务唯一 ID |
| `jti` | 本次 Access Token 的唯一 ID |
| `refreshTokenHash` | Refresh Token 的 SHA-256 十六进制摘要，不保存明文 |
| `createdAt` | Session 创建时间（ISO-8601） |
| `expiresAt` | Session 到期时间（ISO-8601） |

`sessionId` 为去掉连字符的 UUID；`randomSecret` 为 32 字节 `SecureRandom` 的十六进制串。即使 Redis 被读，攻击者也拿不到可用的 Refresh Token 明文。

### 5.4 Rotation 的 Lua 逐行语义

轮换先算出新旧两个 Key：`auth:session:{uid}:{oldSessionId}`（`KEYS[1]`）与 `auth:session:{uid}:{newSessionId}`（`KEYS[2]`），再执行以下脚本（`SessionService.java:36-50`）：

```lua
local expectedHash = redis.call('HGET', KEYS[1], 'refreshTokenHash')
if not expectedHash or expectedHash ~= ARGV[1] then
  return 0
end

redis.call('DEL', KEYS[1])
redis.call('HSET', KEYS[2],
  'uid', ARGV[2],
  'jti', ARGV[3],
  'refreshTokenHash', ARGV[4],
  'createdAt', ARGV[5],
  'expiresAt', ARGV[6])
redis.call('EXPIRE', KEYS[2], ARGV[7])
return 1
```

逐行含义：

1. `HGET` 旧 Session 的 `refreshTokenHash`。旧 Key 不存在时返回 `false`（Lua 里 `not expectedHash` 成立）。
2. 摘要缺失或不等于 `ARGV[1]`（本次提交的旧 Token 的 SHA-256）→ 返回 `0`，**不做任何写入**，旧 Key 原样保留。
3. `DEL` 旧 Key：旧 Refresh Token 立刻作废。
4. `HSET` 新 Key 的五个字段，`jti` 与本次新 Access Token 使用同一个值。
5. `EXPIRE` 新 Key 为 604800 秒。
6. 返回 `1` 表示轮换成功，应用层据此返回新令牌。

| 参数 | 内容 |
| --- | --- |
| `KEYS[1]` / `KEYS[2]` | 旧 / 新 Session Key |
| `ARGV[1]` | 旧 Refresh Token 的 SHA-256 摘要 |
| `ARGV[2]` | `uid` |
| `ARGV[3]` | 新 Access Token 的 `jti` |
| `ARGV[4]` | 新 Refresh Token 的 SHA-256 摘要 |
| `ARGV[5]` / `ARGV[6]` | 新 Session 的 `createdAt` / `expiresAt` |
| `ARGV[7]` | `604800` |

返回值语义：

- `1`：摘要匹配，旧 Session 已删、新 Session 已建，刷新成功。
- `0`：旧 Session 不存在或摘要不匹配，刷新失败且不创建新 Session。

为什么必须放进一次 Lua：早期把“校验”与“轮换”拆成两步（先 `HGET` 比对，再 `HSET` 新 Key），并发下同一个 Refresh Token 能换出两份新会话（典型 TOCTOU），因此校验方法被直接删除，只保留 `rotate`。脚本在 Redis 内单线程原子执行，两个并发请求带同一个旧 Token 时，第一个删掉旧 Key 并建新 Key，第二个 `HGET` 只能拿到 `false` 而返回 `0`，所以旧 Token 天然只能用一次。轮换完成后旧 Key 消失，新 Key 保存新摘要、TTL 7 天。

## 6. 需求六：退出登录

接口 `POST /api/v1/auth/logout`，请求体为空，客户端用 `Authorization: Bearer {accessToken}` 提交当前令牌。JWT 是无状态的，服务端删不掉已签发的 Token，因此采用 **jti 黑名单**：解析出 `jti` 与 `exp`，把 `jti` 写入 Redis，TTL 取剩余寿命。

```text
AuthController.logout
        |
        v
JwtBlacklistService.blacklist(authorization)
        |
        v
校验是否以 "Bearer " 开头（否则 40101 Access Token 无效）
        |
        v
JwtTokenService.parseAndValidate 验签并解析 Claims
        |
        v
取 jti 与 exp，算剩余 TTL
        |
        v
SET auth:blacklist:{jti} = 1 EX 剩余秒数
```

| 项 | 说明 |
| --- | --- |
| Key | `auth:blacklist:{jti}`，如 `auth:blacklist:jti-100` |
| Value | 固定 `1` |
| TTL | Access Token 从当前时间到 `exp` 的剩余秒数 |
| 写入条件 | 签名有效、存在 `jti`、剩余 TTL > 0 |

边界规则：

1. `Authorization` 缺失、不以 `Bearer ` 开头、验签失败或解析异常，统一返回 `40101 Access Token 无效`。
2. 缺少 `jti` 或 Token 已过期（剩余 TTL ≤ 0）时不写黑名单，接口仍返回成功——已过期的 Token 本来就不可用。
3. 黑名单 TTL 永不超过 JWT 剩余寿命，Token 到期后 Key 自然消失，不产生永久垃圾。
4. **退出登录只失效当前 Access Token，不删除 Refresh Session。** Access Token 里只有 `jti`、没有 `sessionId`，要做到“只断当前设备”就得额外维护 `jti → sessionId` 反查索引；当前取舍是不建该索引，需要真正断开用户（全部设备）时用强制下线。
5. 黑名单的实际执法点在 `gateway-service`（`JwtAuthenticationFilter` 查询同一 `auth:blacklist:` 前缀，命中返回 401）；auth-service 自身不拦截受保护请求。

## 7. 需求七：强制下线

接口 `POST /api/v1/auth/force-logout?uid={目标用户uid}`，请求体为空，`Authorization` 携带调用者自己的 Access Token，角色由网关按 JWT `role` claim 注入 `X-User-Role`。

调用者身份与角色**只**来自网关注入的 `X-User-Id` / `X-User-Role`（分别源自 JWT 的 `sub` / `role`），查询参数 `uid` 仅表示操作目标，两者不可混用。

| 条件 | 结果 |
| --- | --- |
| 缺少 `X-User-Id`（未登录或直连绕过网关） | `401` / `40101` |
| 有身份但 `X-User-Role` 不是 `ADMIN`（忽略大小写） | `403` / `40301` |
| 请求体或查询参数里自报 `role=ADMIN` | 不采信，仍按无角色处理 → `403` |
| 角色为 `ADMIN` | 执行下线并返回 `200` |

```text
管理员发起 -> CurrentUser.requireAdmin(request)
                    |
                    v
        SessionService.deleteByUid(uid)      // 清掉该用户全部 Session
                    |
                    v
        JwtBlacklistService.blacklist(authorization)  // 拉黑调用者携带的当前 Access Token
                    |
                    v
              返回成功
```

删除会话用 `SCAN` 而非 `KEYS`（`SessionService.java:123-140`）：按 `auth:session:{uid}:*` 模式、`count 200` 游标迭代收集 Key，再一次性 `DEL`。`KEYS` 是全库 O(N) 扫描并阻塞 Redis 主线程，用户量上来会拖慢同实例上的所有命令。

```text
强制下线
        │
   ┌────┴─────┐
   ▼          ▼
删除 Session  当前 Access Token 黑名单
   │          │
   ▼          ▼
Refresh 不能再刷新  下一次鉴权 401
```

说明：

- 删除 Session 后旧 Refresh Token 再调 `/token/refresh` 只会拿到 Lua 返回的 `0`，即 `40101`。
- 被拉黑的是**调用请求里携带的 Access Token**，不是目标用户的所有历史 Token；目标用户其余设备上的 Access Token 要等各自过期，或由 Session 缺失在后续刷新时被拦住。该能力面向后台管理端/风控，普通用户不应持有 `ADMIN` 角色。

## 8. 需求八：登录接口限流

同一 IP 在 60 秒固定窗口内最多 5 次登录尝试，超限返回 `429` / `42901`“登录请求过于频繁”。

| 项 | 值 |
| --- | --- |
| Key | `auth:login:rate:ip:{ip}` |
| 窗口 | `auth.login-rate-limit.window-seconds`，默认 `60` |
| 上限 | `auth.login-rate-limit.max-attempts`，默认 `5` |
| 超限 | `42901`，HTTP 429 |

```text
INCR auth:login:rate:ip:192.168.1.10
        |
        +-- 返回 1：EXPIRE 60（只有第一次设窗口）
        +-- 返回 2..5：继续登录
        +-- 返回 6 及以上：42901，不查用户、不验密码、不签 Token、不建 Session
```

实现要点：

1. 检查在 `AuthController.login` 调 `AuthService.login` **之前**（`LoginRateLimitService.java:45-58`），被限流的请求不产生任何副作用。
2. 只有 `INCR` 返回 `1` 时才 `EXPIRE`，后续请求不重置窗口，否则持续请求会把窗口无限续期。
3. 计数按“尝试”累加，**登录成功即 `DEL` 该 Key**（`onLoginSuccess`），实际效果是只统计连续失败次数；否则正常用户一分钟内连登几次就会被误限。
4. IP 取自 `HttpServletRequest#getRemoteAddr()`。经网关访问时它是网关地址，因此 `application.yml` 开了 `server.forward-headers-strategy: framework`，由 Spring 按 `X-Forwarded-For` 还原真实客户端地址；否则所有客户端共用一个桶，任何人刷 5 次就能让全站一分钟无法登录。
5. `X-Forwarded-For` 可被伪造（网关侧同样是取第一个值），直连或伪造该头即可绕过限流，生产环境需在入口层覆写该头。
6. 固定窗口在边界处会出现跨两个窗口的短时突刺；需要更平滑时可换滑动窗口或令牌桶（网关的 `gateway:rate:*` 已是令牌桶 Lua），登录这一层当前仍是 `INCR` + `EXPIRE`。
## 9. MySQL 总体结构

`account` 表由 `auth-service/src/main/resources/schema.sql` 在启动时建（`spring.sql.init.mode=always`）。完整 DDL、建表顺序与幂等性说明见 [deploy/db/README.md](../deploy/db/README.md)，本文只列结构约束：

| 列 | 类型 | 约束与用途 |
| --- | --- | --- |
| `id` | `BIGINT` | 自增主键，**不对外暴露** |
| `uid` | `VARCHAR(32)` | 业务唯一 ID，JWT `sub` 与 Redis Session 都用它；`uk_uid` |
| `username` | `VARCHAR(32)` | 当前链路恒为 `NULL`，为将来的用户名登录预留；`uk_username` |
| `phone` | `VARCHAR(20)` | 手机号注册时有值；`uk_phone` |
| `email` | `VARCHAR(254)` | 邮箱注册时有值；`uk_email` |
| `password_hash` | `VARCHAR(100)` | BCrypt 摘要，非明文 |
| `status` | `TINYINT` | 默认 `1`；登录要求 `status = 1` |
| `created_at` / `updated_at` | `DATETIME` | 审计时间 |

唯一索引负责并发注册的最终一致性；“手机号与邮箱二选一”由应用层保证（两条注册路径各自把另一列写 `NULL`）。

## 10. Redis 总体规则

| 数据 | Key | Value | TTL |
| --- | --- | --- | --- |
| 验证码 | `auth:verification:{purpose}:{type}:{target}` | 6 位数字 | 180 秒 |
| 发送冷却 | `auth:verification:{purpose}:{type}:{target}:cooldown` | `1` | 60 秒 |
| Session | `auth:session:{uid}:{sessionId}` | Hash（`uid`/`jti`/`refreshTokenHash`/`createdAt`/`expiresAt`） | 604800 秒 |
| JWT 黑名单 | `auth:blacklist:{jti}` | `1` | 不超过 JWT 剩余 TTL |
| 登录限流 | `auth:login:rate:ip:{ip}` | 计数值 | 窗口 60 秒 |

顺序约束：

- 发送验证码：检查冷却 → 生成 → Provider 发送成功 → 写验证码 Key → 写 cooldown Key。
- 校验验证码：读取 → 比较 → 比较成功后删除 → 执行业务。
- 刷新令牌：一段 Lua 内完成“比对摘要 → 删旧 Key → 建新 Key”。

尚未实现的部分：验证码发送的 `SET NX EX`/Lua 化、按 IP/设备/目标地址的多维验证码限制、`jti → sessionId` 反查索引（做“单设备登出”用）。当前 Lua 只出现在网关全局限流、网关 IP 限流、Refresh Token 轮换、弹幕双层限流四处，auth-service 内只有 Refresh 轮换用了 Lua。
