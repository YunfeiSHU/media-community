# Auth-Service技术方案

## 文档信息

| 项目 | 内容 |
| --- | --- |
| 服务名称 | `auth-service` |
| 文档版本 | `1.0` |
| 技术基线 | Java 17、Spring Boot 3.3.5、MyBatis 3.0.3、MySQL 8、Redis 7 |
| 核心能力 | 手机号/邮箱注册与登录、验证码、JWT、Refresh Token Rotation、注销黑名单 |

## 总体设计

### 系统边界

`auth-service` 负责账号身份注册、凭据校验和 Token 生命周期管理，不承载用户资料、权限模型或业务资源。客户端通过 HTTP JSON 接口访问服务；账号数据写入本服务 MySQL 的 `account` 表，用户资料由 `user-service` 管理。短生命周期验证码、登录 Session 和 JWT 黑名单写入 Redis。

```text
Client
  |
  v
AuthController  ---- 参数校验 / 统一响应
  |
  v
AuthService / VerificationService
  |                     |
  v                     v
MyBatis -> account 表    StringRedisTemplate -> Redis
  |
  +---- PasswordEncoder（BCrypt）
  +---- JwtTokenService（HMAC JWT）
  +---- SMS / Email NotificationProvider
  +---- UserServiceClient -> Dubbo -> user-service
```

### 分层职责

| 层级 | 主要职责 |
| --- | --- |
| Controller | 接收请求、执行 Bean Validation、调用业务服务、封装统一响应 |
| Service | 注册登录编排、验证码管理、JWT 生成解析、Session Rotation、注销黑名单 |
| Repository | 使用 MyBatis 读写 `account` 表 |
| Provider | 隔离短信和邮件发送渠道，便于替换真实供应商 |
| MySQL | 保存账号联系方式、密码摘要、状态和审计时间，不保存用户资料 |
| Redis | 保存验证码、发送冷却、Refresh Session 和 Access Token 黑名单 |

### 核心设计原则

1. 密码只保存 BCrypt 摘要，Refresh Token 只保存 SHA-256 摘要。
2. JWT 使用不可变业务标识 `uid` 作为 `sub`，不暴露数据库自增主键。
3. MySQL 唯一索引负责并发注册的最终一致性保护。
4. Refresh Token 每次刷新都轮换，并通过 Redis Lua 保证旧 Session 删除与新 Session 创建的原子性。
5. 验证码、Session 和黑名单均设置 TTL，避免无期限数据累积。

### 跨服务用户创建

注册采用 auth-service 编排、user-service 负责资料落库的两阶段流程。Dubbo 调用不是注册事务的边界，不能依赖一次同步 RPC 同时完成两边数据库写入；调用必须具备幂等键、超时重试和失败补偿能力。

#### 新注册流程

1. auth-service 校验验证码、联系方式和密码，并将手机号/邮箱标准化。
2. auth-service 生成 `registrationId`，以注册请求为粒度保存注册状态。相同请求重试时复用该值，禁止重新创建用户。
3. auth-service 通过 Dubbo 调用 `createUser`，请求携带 `registrationId` 和资料字段。user-service 以 `registrationId` 做幂等判断：首次请求生成唯一 `uid` 并创建资料；重复请求直接返回第一次创建结果。
4. auth-service 校验返回结果中的 `uid`，在本地事务中写入 `account.uid`、联系方式和密码摘要。两张表仅通过共享 `uid` 关联，不使用 `user_id` 或对方数据库的内部 `id`。
5. account 写入成功后，注册状态标记为 `COMPLETED`，再签发 JWT/Refresh Token。Token 的 `sub` 使用该 `uid`。
6. Dubbo 超时或网络异常时，auth-service 先查询注册状态/按幂等键重试，不直接再次生成注册请求。超过重试上限后标记为 `PENDING_RECONCILIATION`，由后台对账任务继续处理。
7. user-service 创建成功但 account 落库失败时，禁止静默忽略。补偿任务根据 `registrationId` 重试 account 落库；确认注册最终失败后，再调用 user-service 的补偿接口执行逻辑删除。

#### Dubbo 契约约定

`CreateUserCommand` 应增加 `registrationId`，返回结果至少包含 `uid` 和幂等处理状态。建议补充以下接口：

```text
createUser(CreateUserCommand command)
getRegistration(String registrationId)
cancelRegistration(String registrationId)
```

`getUser`、`batchGetUsers` 和 `checkUserExists` 继续使用 `String uid`；它们只读 user-service 数据，不参与注册事务。所有写接口都必须设置调用超时、有限次数重试和明确的业务异常映射；禁止对非幂等请求进行无限重试。

两边使用直连 Dubbo 配置时，user-service 默认监听 `20880`，auth-service 默认调用 `dubbo://localhost:20880`；可通过 `USER_SERVICE_DUBBO_URL` 覆盖地址。生产环境应使用注册中心或服务发现，并将 RPC DTO/interface 抽取为共享 API 模块。

## 公共约定

### 账号规则

- 新用户必须使用手机号或邮箱注册。
- `username` 不再参与注册、登录，也不建立唯一索引。
- 手机号和邮箱分别建立唯一索引。
- 一个新用户只能绑定一种注册身份：手机号注册时 `phone` 有值、`email` 为空；邮箱注册时相反。
- 邮箱统一转小写后再写入和查询；手机号按中国大陆 11 位格式校验。

### 统一响应结构

成功：

```json
{
  "code": 0,
  "message": "success",
  "data": null
}
```

失败：

```json
{
  "code": 1001,
  "message": "验证码无效或已过期",
  "data": null
}
```

错误码：`0` 成功，`1001` 业务失败，`1002` 参数校验失败。

HTTP 状态码约定：成功返回 `200 OK`；业务规则不满足或请求参数校验失败返回 `400 Bad Request`；未捕获的基础设施异常由服务端按 `500 Internal Server Error` 处理。无论成功或已纳入统一异常处理的失败，响应体都保持上述结构。

### 数据标准化与时间约定

- 手机号去除首尾空格后校验，当前仅支持中国大陆 `1[3-9]` 开头的 11 位号码。
- 邮箱去除首尾空格并统一转为小写，标准化结果用于查询、写入和 Redis Key。
- 服务端时间字段使用 ISO-8601 字符串写入 Redis；MySQL 审计字段使用 `DATETIME`。
- Token 有效期与 Redis TTL 均以秒为单位，服务端是有效期计算的唯一可信来源。

## 1. 需求一：发送手机或邮箱验证码

### 1.1 接口

```http
POST /api/v1/auth/verification/send
Content-Type: application/json
```

### 1.2 请求文 JSON

手机号：

```json
{
  "purpose": "register",
  "type": "phone",
  "target": "13800138000"
}
```

邮箱：

```json
{
  "purpose": "register",
  "type": "email",
  "target": "user@example.com"
}
```

字段：

| 字段 | 必填 | 可选值/格式 | 说明 |
| --- | --- | --- | --- |
| `purpose` | 是 | `register`、`login`、`reset_password` | 验证码用途 |
| `type` | 是 | `phone`、`email` | 发送渠道 |
| `target` | 是 | 手机号或邮箱 | 接收目标 |

### 1.3 响应文 JSON

短信学习模式响应：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "purpose": "register",
    "type": "phone",
    "target": "13800138000",
    "code": "123456"
  }
}
```

邮箱响应：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "purpose": "register",
    "type": "email",
    "target": "user@example.com",
    "code": null
  }
}
```

频繁发送：

```json
{
  "code": 1001,
  "message": "验证码获取过于频繁",
  "data": null
}
```

> 由于当前是学习开发，短信验证码直接返回。生产环境必须删除 `data.code`，避免验证码泄露。

### 1.4 设计流程

```text
接收 purpose + type + target
              |
              v
校验 target 并标准化邮箱/手机号
              |
              v
检查 Redis cooldown Key
       |                 |
      存在               不存在
       |                 |
返回“获取过于频繁”     生成 6 位验证码
                             |
                             v
                    调用 SMS/Email Provider
                       |             |
                    发送失败        发送成功
                       |             |
                 不写入 Redis     保存验证码 Key
                                      |
                                      v
                                保存 cooldown Key
                                      |
                                      v
                                    返回响应
```

### 1.5 MySQL 设计

发送验证码不读写 MySQL。发送前可在后续版本增加业务校验，例如注册时检查联系方式是否已注册，但当前注册重复性由注册流程和唯一索引保证。

### 1.6 Redis 设计

验证码 Key：

```text
auth:verification:{purpose}:{type}:{target}
```

示例：

```text
auth:verification:register:phone:13800138000
```

- Value：6 位数字字符串，例如 `123456`
- TTL：180 秒

冷却 Key：

```text
auth:verification:{purpose}:{type}:{target}:cooldown
```

- Value：`1`
- TTL：60 秒
- Key 存在时拒绝重复发送

写入顺序必须是：通知发送成功 -> 写入验证码 Key -> 写入 cooldown Key。发送失败时不能写入 Redis。

## 2. 需求二：手机号注册

### 2.1 接口

```http
POST /api/v1/auth/register/phone
Content-Type: application/json
```

### 2.2 请求文 JSON

```json
{
  "phone": "13800138000",
  "code": "123456",
  "password": "Abc123456"
}
```

校验规则：手机号为 `1[3-9]` 开头的 11 位数字；验证码为 6 位数字；密码长度为 8~20 个字符。

### 2.3 响应文 JSON

注册成功：

```json
{
  "code": 0,
  "message": "success",
  "data": null
}
```

验证码失败：

```json
{
  "code": 1001,
  "message": "验证码无效或已过期",
  "data": null
}
```

手机号已注册：

```json
{
  "code": 1001,
  "message": "联系方式已注册",
  "data": null
}
```

### 2.4 设计流程

```text
接收 phone + code + password
             |
             v
校验手机号、验证码、密码格式
             |
             v
读取 Redis 验证码 Key
       |                  |
  不存在/不匹配          匹配
       |                  |
    返回失败         删除验证码 Key
                            |
                            v
             查询 MySQL phone 是否存在
                       |             |
                      是             否
                       |             |
                 返回已注册       BCrypt 加密密码
                                          |
                                          v
                                   写入 MySQL user
                                          |
                                          v
                                        注册成功
```

### 2.5 MySQL 设计

写入 `account` 表：

| 字段 | 写入值 |
| --- | --- |
| `user_id` | user-service 返回的数据库主键 |
| `uid` | user-service 返回的业务 UID |
| `phone` | 标准化后的手机号 |
| `email` | `NULL` |
| `password_hash` | BCrypt 加密后的密码 |
| `status` | `1` |
| `created_at` | 当前时间 |
| `updated_at` | 当前时间 |

查询和最终防重：

```sql
SELECT id, user_id, uid, phone, email, password_hash, status,
       created_at, updated_at
FROM `account`
WHERE phone = ? OR email = ?
LIMIT 1;
```

Repository 当前使用统一联系方式查询，手机号注册时传入标准化手机号，因此仅 `phone` 分支能够命中。`phone` 使用唯一索引 `uk_phone`，并发注册时即使应用层查询同时返回为空，数据库仍能阻止重复数据。用户资料由 Dubbo 调用 user-service 创建和查询。

### 2.6 Redis 设计

读取：

```text
auth:verification:register:phone:13800138000
```

校验成功后立即删除该 Key，保证验证码只能使用一次。冷却 Key 不需要因注册成功而删除，继续按 60 秒自然过期即可。

```text
              |
```

```text
标准化手机号或邮箱
```

### 4.5 MySQL 设计

```sql
       created_at, updated_at

```

当前 Repository 通过 `phone = ? OR email = ?` 同时兼容手机号和邮箱，参数在查询前已按登录类型标准化。登录只校验密码，不写入 MySQL。后续增加登录审计时，可新增登录日志表记录用户、IP、设备和结果。

### 4.6 Redis 设计

登录成功后会创建 Redis Session，用于保存 Refresh Token 会话状态，并保存本次 Access Token 的 `jti`。Access Token 本身不保存到 Redis；注销时只将其 `jti` 写入 Redis 黑名单。

登录失败限制可使用：

```text
auth:login:fail:{type}:{target}
```

用于失败次数限制和临时锁定；登录成功后删除失败计数 Key。

## 5. 需求五：Access Token 与 Refresh Token 生命周期

```text
                         登录
                          │
                          ▼
                    用户身份认证
                          │
                          ▼
                  ┌───────────────┐
                  │ 创建 Session  │
                  │    Redis     │
                  └───────┬───────┘
                          │
              ┌───────────┴───────────┐
              ▼                       ▼
       Access Token             Refresh Token
          JWT                     Random
        30分钟                     7天
              │                       │
              ▼                       ▼
         访问业务 API             Token Refresh
              │                       │
              ▼                       ▼
          JWT 验证                 Redis Session
              │                       │
              ▼                       ▼
           userId                新 Access Token
```

### 5.1 登录时生成 Token

登录成功后的调用链：

```text
AuthController.login
        |
        v
AuthService.login
        |
        +--> UserRepository --> MySQL user
        |
        +--> BCrypt 校验 password_hash
        |
      +--> 校验 status = 1
      |
      +--> JwtTokenService --> 生成并签名 Access Token（JWT，30 分钟）
        |
      +--> SessionService --> Redis Session（7 天，保存 jti）
        |
        v
返回 LoginResponse
```

登录响应：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "uid": "7f1f8c9b5e0a4b8c9f2c1d3e4a5b6c7d",
    "accessToken": "eyJhbGciOiJIUzI1NiJ9...",
    "refreshToken": "7f1f8c9b5e0a4b8c9f2c1d3e4a5b6c7d.session-id.random-secret",
    "accessTokenExpiresIn": 1800,
    "refreshTokenExpiresIn": 604800
  }
}
```

Access Token 是 JWT，过期时间 30 分钟；Refresh Token 是随机不透明字符串，过期时间 7 天。客户端只应将 Token 保存在安全存储中。

**JWT 生成规则：**

1. 根据 `type + target` 从 MySQL 查询用户。
2. 用户不存在、状态不是 `1` 或 BCrypt 密码校验失败时，立即返回登录失败，不生成任何 Token。
3. 使用用户 `uid` 作为 JWT `sub`（Subject），不使用数据库自增 `id`。
4. 生成唯一 `jti`，写入 JWT 的 `jti` Claim。
5. 写入 `iat`（签发时间）和 `exp`（过期时间）Claims。
6. 使用服务端配置的 HMAC 密钥签名 JWT，密钥不能由客户端传入，也不能提交到代码仓库。
7. 生成 Refresh Token，并在 Redis Session 中保存相同的 `jti`。
8. Redis Session 写入成功后再向客户端返回完整 `LoginResponse`。

JWT Payload 示例：

```json
{
  "sub": "7f1f8c9b5e0a4b8c9f2c1d3e4a5b6c7d",
  "jti": "jti-100",
  "iat": 1726754400,
  "exp": 1726756200
}
```

业务接口校验 Access Token 时必须校验：签名、`exp`、`sub`、`jti` 非空，并检查 `auth:blacklist:{jti}` 是否存在；不能只解码而不验证签名。

### 5.2 JWT 黑名单与注销

接口：

```http
POST /api/v1/auth/logout
Authorization: Bearer {accessToken}
```

注销成功响应：

```json
{
  "code": 0,
  "message": "success",
  "data": null
}
```

注销流程：

```text
客户端提交 Access Token
          |
          v
JwtTokenService 验签并解析 jti、exp
          |
          v
计算 JWT 剩余有效时间
          |
          v
SET auth:blacklist:{jti} = 1 EX 剩余秒数
          |
          v
后续鉴权发现 Key 存在，拒绝使用该 JWT
```

Redis Key：

```text
auth:blacklist:{jti}
```

Value 为 `1`。Blacklist TTL 使用 JWT 的剩余有效秒数，绝不会超过 JWT 本身的剩余生命周期；JWT 过期后黑名单 Key 自然失效，不产生永久垃圾数据。

如果 Token 已过期或剩余 TTL 小于等于 0，不写入黑名单。无效签名、缺少 `Bearer` 加空格的前缀或缺少 `jti` 时返回 `Access Token 无效`。

### 5.3 Refresh Token 刷新

接口：

```http
POST /api/v1/auth/token/refresh
Content-Type: application/json
```

请求文：

```json
{
  "refreshToken": "7f1f8c9b5e0a4b8c9f2c1d3e4a5b6c7d.session-id.random-secret"
}
```

成功响应文：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "uid": "7f1f8c9b5e0a4b8c9f2c1d3e4a5b6c7d",
    "accessToken": "eyJhbGciOiJIUzI1NiJ9...new-access-token",
    "refreshToken": "7f1f8c9b5e0a4b8c9f2c1d3e4a5b6c7d.session-id.random-secret",
    "accessTokenExpiresIn": 1800,
    "refreshTokenExpiresIn": 604800
  }
}
```

失败响应文：

```json
{
  "code": 1001,
  "message": "Refresh Token 无效或已过期",
  "data": null
}
```

**刷新流程：**

```text
客户端提交 Refresh Token
          |
          v
SessionService 校验 Token 格式并解析 uid/sessionId
          |
          v
生成新 jti、sessionId 和 Refresh Token
      |
      v
Redis Lua 原子校验旧 refreshTokenHash
       |                         |
   不存在/摘要不匹配             匹配
       |                         |
  返回失败         删除旧 Session 并创建新 Session
                                  |
                                  v
             JwtTokenService
                                  |
                                  v
             使用新 jti 生成 Access Token
                  |
                  v
          返回新 Access Token 与 Refresh Token
```

刷新成功后必须轮换 Refresh Token：原子删除旧 Session，创建新的 Session，并返回新的 Refresh Token。旧 Refresh Token 立即失效，不能再次刷新。

### 5.4 Redis Session

用户表通过 `uid` 作为业务唯一用户 ID。JWT 的 `sub` 和 Redis Session 均使用 `uid`，不直接使用或暴露 MySQL 自增 `id`。

**Redis Session Key：**

```text
auth:session:{uid}:{sessionId}
```

Redis Hash 字段：

| 字段               | 说明                                      |
| ------------------ | ----------------------------------------- |
| `uid`              | 用户业务唯一 ID                           |
| `jti`              | 本次 Access Token 的唯一 ID               |
| `refreshTokenHash` | Refresh Token 的 SHA-256 摘要，不保存明文 |
| `createdAt`        | Session 创建时间                          |
| `expiresAt`        | Session 到期时间                          |

Session TTL 为 604800 秒，即 7 天。登录流程查询 MySQL 用户并校验密码，随后创建 Redis Session；刷新流程原子校验并删除旧 Redis Session、创建新 Session，再生成新的 Access Token，不重复查询密码。

刷新时会生成新的 `jti`，新 JWT 和新 Redis Session 使用同一个 `jti`；旧 Session 和旧 Refresh Token 同时失效。

### 5.5 Redis Rotation 原子设计

Refresh Token 的格式为：

```text
{uid}.{sessionId}.{randomSecret}
```

旧 Token 对应旧 Key：

```text
auth:session:{uid}:{oldSessionId}
```

轮换时先生成新的 `sessionId` 和随机 Refresh Token，但不直接暴露或单独写入；然后通过一次 Redis Lua 脚本完成校验和替换。

Lua 脚本逻辑：

```lua
local expectedHash = redis.call('HGET', KEYS[1], 'refreshTokenHash')
if not expectedHash or expectedHash ~= ARGV[1] then
  return 0
end

redis.call('DEL', KEYS[1])
redis.call('HSET', KEYS[2],
  'uid', ARGV[2],
  'jti', ARGV[3],
  'refreshTokenHash', ARGV[4],
  'createdAt', ARGV[5],
  'expiresAt', ARGV[6])
redis.call('EXPIRE', KEYS[2], ARGV[7])
return 1
```

参数说明：

| 参数 | 内容 |
| --- | --- |
| `KEYS[1]` | 旧 Session Key |
| `KEYS[2]` | 新 Session Key |
| `ARGV[1]` | 旧 Refresh Token 的 SHA-256 摘要 |
| `ARGV[2]` | 用户 `uid` |
| `ARGV[3]` | 新 Access Token 的 `jti` |
| `ARGV[4]` | 新 Refresh Token 的 SHA-256 摘要 |
| `ARGV[5]` | 新 Session 创建时间 |
| `ARGV[6]` | 新 Session 过期时间 |
| `ARGV[7]` | `604800`，Session TTL 秒数 |

返回值：

- `1`：旧 Token 摘要匹配，旧 Session 已删除，新 Session 已创建，刷新成功
- `0`：旧 Session 不存在或摘要不匹配，刷新失败，不创建新 Session

Lua 脚本在 Redis 内部原子执行。两个并发请求使用同一个旧 Refresh Token 时，第一个请求删除旧 Key 并创建新 Key；第二个请求再读取旧 Key 时只能得到 `0`，因此旧 Token 只能成功使用一次。

轮换后的 Redis 状态：

```text
旧 Key auth:session:{uid}:{oldSessionId} -> 已删除
新 Key auth:session:{uid}:{newSessionId} -> 保存新 refreshTokenHash，TTL 7 天
```

服务端只在 Redis 中保存摘要，不保存任何 Refresh Token 明文。测试应至少覆盖：轮换成功返回新 Token、Redis 返回 `0` 时拒绝、格式非法时拒绝、旧 Token 不能二次轮换。

## 需求六：退出登录

退出登录用于让当前 Access Token 提前失效。由于 JWT 本身是无状态 Token，服务端不能直接删除已经签发的 JWT，因此当前实现采用 **JWT 黑名单** 方案：退出时解析 Access Token 的 `jti`，将该 `jti` 写入 Redis 黑名单，并设置与 JWT 剩余生命周期一致的 TTL。

### 接口

```http
POST /api/v1/auth/logout
Authorization: Bearer {accessToken}
```

请求体为空。客户端必须通过 `Authorization` 请求头提交当前 Access Token。

### 响应文 JSON

退出成功：

```json
{
  "code": 0,
  "message": "success",
  "data": null
}
```

Access Token 无效：

```json
{
  "code": 1001,
  "message": "Access Token 无效",
  "data": null
}
```

### 实现流程

```text
AuthController.logout
          |
          v
AuthService.logout
          |
          v
JwtBlacklistService.blacklist
          |
          v
校验 Authorization 是否以 Bearer 开头
          |
          v
JwtTokenService.parseAndValidate 验签并解析 Claims
          |
          v
读取 jti 和 exp，计算剩余 TTL
          |
          v
SET auth:blacklist:{jti} = 1 EX 剩余秒数
          |
          v
返回退出成功
```

### Redis 黑名单设计

Redis Key：

```text
auth:blacklist:{jti}
```

示例：

```text
auth:blacklist:jti-100
```

| 字段     | 说明                                        |
| -------- | ------------------------------------------- |
| Value    | 固定为 `1`                                  |
| TTL      | Access Token 从当前时间到 `exp` 的剩余秒数  |
| 写入条件 | Token 签名有效、存在 `jti`、剩余 TTL 大于 0 |

黑名单 Key 的 TTL 不超过 JWT 自身剩余有效期。JWT 到期后即使黑名单 Key 消失，该 Token 也会因 `exp` 过期而无法继续使用，因此不会产生长期无效数据。

### 边界规则

1. `Authorization` 为空或不以 `Bearer` 加空格开头时，返回“Access Token 无效”。
2. JWT 签名非法、格式错误或解析失败时，返回“Access Token 无效”。
3. JWT 缺少 `jti` 或已经过期时，不写入黑名单，接口仍可结束处理。
4. 退出登录只让当前 Access Token 提前失效，不会删除 Refresh Token Session。
5. 如果需要“退出后 Refresh Token 也失效”，后续应在退出接口中同时定位并删除 `auth:session:{uid}:{sessionId}`，或提供全端注销接口。

### 后续鉴权要求

退出登录写入黑名单只是失效机制的一半。所有受保护业务接口在校验 Access Token 时都必须执行以下检查：

1. 验证 JWT 签名和 `exp`。
2. 校验 `sub` 和 `jti` 非空。
3. 查询 `auth:blacklist:{jti}` 是否存在。
4. 如果黑名单 Key 存在，拒绝本次访问。

当前项目已实现 `JwtBlacklistService.isBlacklisted(jti)`，可供后续鉴权过滤器调用。

## 需求七：强制下线

强制下线用于管理员或安全策略在检测到风险登录、账号异常、密码泄露或合规要求时，立即让用户失去当前会话能力。该操作要求同时使两类凭证失效：

- Refresh Token 失效：旧 Refresh Token 不能继续刷新，必须禁止 `POST /api/v1/auth/token/refresh` 成功执行。
- Access Token 立即失效：当前 JWT 必须在下一次鉴权检查时返回 `401 Unauthorized`。

```text
    强制下线
                   │
        ┌──────────┴──────────┐
        ▼                     ▼
删除 Redis Session       Access Token Blacklist
        │                     │
        ▼                     ▼
Refresh Token 失效        当前 JWT 失效
```

### 设计目标

1. 删除用户当前 Redis Session，确保旧 Refresh Token 无法再次轮换。
2. 把当前 Access Token 的 `jti` 写入 Redis 黑名单，确保后续鉴权立即返回 `401`。
3. 让客户端感知“下线后需要重新登录”，而不是继续使用旧 Token。
4. 维持最小化改动：不要求全部历史 Token 失效，只要求当前有效会话和当前 Access Token 失效。

### 业务流程

```text
管理员或安全组件发起强制下线
          |
          v
根据 uid 定位当前 Session
          |
          +------> 删除 Redis Session Key
          |               auth:session:{uid}:{sessionId}
          |
          +------> 读取当前 Access Token 的 jti
          |
          +------> SET auth:blacklist:{jti} = 1 EX 剩余 TTL
          |
          v
返回强制下线成功
```

### 失效效果

```text
Refresh Token
    ↓
不能刷新
```

```text
Access Token
    ↓
立即 401
```

### 实现要点

- 需要知道用户当前的 `uid` 和当前 `sessionId`；在 Redis 中删除对应 Session Key 即可确保旧 Refresh Token 失效。
- 需要解析并保留当前 Access Token 的 `jti`，并**写入 `auth:blacklist:{jti}`；其 TTL 不能超过 JWT 剩余有效期。**
- 若业务层在鉴权拦截器中已检查黑名单和 Session，强制下线后客户端拿到的旧 Token 会在下一次请求被拒绝。
- 该能力通常由后台管理端、风控策略或账号安全中心触发，而不是普通用户自行调用。



## 需求八：登录接口限流

为防止同一 IP 在短时间内反复尝试登录，登录接口使用 Redis 实现基于 IP 的固定窗口限流。当前策略为：同一 IP 在 60 秒窗口内最多请求 5 次，超过后拒绝登录请求。

### 限流规则

```text
窗口：60 秒
最大请求数：5 次
Key：auth:login:rate:ip:{ip}
超限错误码：1003
```

固定窗口计数流程：

```text
INCR auth:login:rate:ip:192.168.1.10
              |
              +-- 返回 1：设置 EXPIRE 60
              |
              +-- 返回 2 至 5：继续登录流程，不重置 TTL
              |
              +-- 返回 6 及以上：拒绝请求
```

### 实现要求

1. 限流检查在 `AuthController.login` 调用 `AuthService.login` 之前执行。
2. 第一次计数时设置 `EXPIRE 60`，后续请求不能重置窗口过期时间。
3. 计数超过 5 时返回 HTTP 400、业务码 `1003` 和消息“登录请求过于频繁”。
4. 被限流的请求不能查询用户、校验密码、生成 JWT 或创建 Session。
5. 限流 Key 使用客户端 IP 隔离，不同 IP 使用不同计数窗口。

### Redis 数据示例

```text
auth:login:rate:ip:192.168.1.10 = 5
TTL = 60 秒以内
```

该实现属于固定窗口算法。窗口边界处可能出现短时间内跨两个窗口累计请求的情况；如后续需要更平滑的限流效果，可升级为滑动窗口或令牌桶算法。

## 7. MySQL 总体结构

```sql
CREATE TABLE IF NOT EXISTS `account` (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    uid VARCHAR(32) NOT NULL,
    phone VARCHAR(20) NULL,
    email VARCHAR(254) NULL,
    password_hash VARCHAR(100) NOT NULL,
    status TINYINT NOT NULL DEFAULT 1,
    created_at DATETIME NOT NULL,
    updated_at DATETIME NOT NULL,
    UNIQUE KEY uk_phone (phone),
    UNIQUE KEY uk_email (email),
    UNIQUE KEY uk_uid (uid)
);
```

`account` 只保存认证边界内的字段；`user_id` 保存 user-service 返回的用户主键，`uid` 保存对外使用的稳定业务标识。MySQL 唯一索引保证手机号、邮箱和 uid 不能重复；应用服务层保证新用户手机号和邮箱二选一。

## 8. Redis 总体规则

| 数据 | Key | Value | TTL |
| --- | --- | --- | --- |
| 验证码 | `auth:verification:{purpose}:{type}:{target}` | 6 位数字 | 180 秒 |
| 发送冷却 | `auth:verification:{purpose}:{type}:{target}:cooldown` | `1` | 60 秒 |
| Session | `auth:session:{uid}:{sessionId}` | Redis Hash | 604800 秒 |
| JWT 黑名单 | `auth:blacklist:{jti}` | `1` | 不超过 JWT 剩余 TTL |

发送验证码的固定顺序：检查冷却 -> 生成验证码 -> 调用 Provider -> 发送成功后写入两个 Key。

校验验证码的固定顺序：读取验证码 -> 比较 -> 比较成功后删除验证码 Key -> 执行业务操作。

生产环境需要使用 Redis Lua 或 `SET NX EX` 解决并发发送竞态，并增加 IP、设备、目标地址和验证码错误次数限制。
