# product-service / order-service 对外 HTTP 接口测试文档

> 覆盖范围：两个服务**对外暴露的 HTTP 接口**（不含 Dubbo RPC，不含定时任务、内部补偿逻辑）。
> 每个接口给出：路径 / 鉴权要求 / 请求体 / curl 命令 / 预期结果（含失败场景）。
> 文档内容与当前代码逐字段核对过：`ProductController`、`SkuController`、`OrderController`、`PaymentController`、
> 各 `*Request` / `*VO`、`ErrorCode`、`GlobalExceptionHandler`、`gateway-service/application.yml`。

## 1. 测试环境与前置条件

### 1.1 依赖组件

| 组件 | 默认地址 | 用途 |
| --- | --- | --- |
| MySQL | `localhost:3306/auth_service` | 两个服务共用库（product/order 表都在该库） |
| Redis | `localhost:6379` | 网关限流 / JWT 黑名单 |
| Nacos | `localhost:8848` | 服务发现（网关用 `lb://` 路由） |

### 1.2 服务端口

| 服务 | 端口 | 对外基址（直连） |
| --- | --- | --- |
| gateway-service | 8000 | `http://localhost:8000` |
| product-service | 8003 | `http://localhost:8003` |
| order-service | 8004 | `http://localhost:8004` |

### 1.3 两种访问方式（务必先选定一种）

| 方式 | 地址 | 鉴权 |
| --- | --- | --- |
| **经网关**（推荐，贴近真实链路） | `http://localhost:8000` | 需要 `Authorization: Bearer <jwt>`；网关校验 JWT 后把 `sub`（用户 uid）写入 `X-User-Id`、角色写入 `X-User-Role` 转发下游 |
| **直连服务**（联调、排障） | `http://localhost:8003` / `:8004` | 服务本身**不做 JWT 校验**。两个服务都只从 `X-User-Id` 取当前用户，直连时必须手工补上，否则返回 `401/40101` |

**身份传递约定（各服务统一）**

| 项 | 约定 |
| --- | --- |
| uid 来源 | JWT 标准 claim `sub`（auth-service 签发时写入用户 uid），网关固定从此取值，无可配置的 claim 名 |
| 角色来源 | JWT 的 `role` claim（值 `ADMIN` / `user`），缺失按 `user` 处理；claim 名由 `gateway.auth.jwt.role-claim` 指定，须与 auth-service 签发时一致 |
| 下游可见头 | `X-User-Id` / `X-User-Role`，由网关**先清后写**，客户端伪造无效 |
| 下游服务 | 只信任上述两个头：**不解析 JWT**、**不接受**请求体 / 查询参数里的用户标识**与角色** |
| 需要角色的接口 | 角色只能从 `X-User-Role` 读（见 `CurrentUser.role()`）。当前仅 auth-service 的 `force-logout` 按角色鉴权（须 `ADMIN`） |
| 缺身份头 | `401 / 40101`（auth / user / product / order 一致） |
| 角色不足 | `403 / 40301`（`ErrorCode.FORBIDDEN`） |
| 资源归属 | product-service 的商品 / SKU / 价格 / 库存**写接口只允许商品创建者**（`product.uid` == `X-User-Id`），他人调用 → `403 / 40301`；order-service 查他人订单 → `404 / 40401`（刻意不暴露存在性） |
| 白名单路径 | 网关会先清掉 `X-User-Id` / `X-User-Role` / 历史头 `uid` 再放行 |
| 历史兼容 | 早期网关注入的非标准头 `uid` 已不再下发，服务侧仅做兜底读取 |

网关路由（`gateway-service/application.yml`）：

```yaml
product-service: Path=/api/v1/products/**,/api/v1/skus/**
order-service:   Path=/api/v1/orders/**,/api/v1/payments/**
```

**JWT 白名单（免登录路径）**

| 白名单项 | 影响 |
| --- | --- |
| `GET /api/v1/products/*` | 商品详情免登录（Ant 的 `*` 只匹配单段，**不**匹配 `/products/{id}/skus`） |
| `GET /api/v1/skus/*` | 仅 `GET /skus/{id}` 免登录；`GET /skus/{id}/price`、`/stock` 及所有写操作**仍需 JWT** |
| `POST /api/v1/payments/callback` | 支付回调免登录（渠道服务器无令牌）；该分支会清掉客户端伪造的 `uid` / `X-User-Id` / `X-User-Role` |
| `/api/v1/orders/**` | **不在白名单**，全部需要 JWT |

### 1.5 统一响应结构与序列化约定

```json
{ "code": 0, "message": "success", "data": { } }
```

- `code = 0` 表示成功，其它值见 §1.6 错误码表；HTTP 状态码与错误码前缀一致（40001 → 400）。
- 两个服务都配置了 `spring.jackson.default-property-inclusion: non_null`：
  **值为 null 的字段会从 JSON 中整体消失**。例如删除成功返回 `{"code":0,"message":"success"}`（没有 `data`），
  未传 `description` 的商品详情里不会出现 `description` 字段。断言时不要写 `"data": null`。
- 时间为 `LocalDateTime`，序列化为 `2026-09-22T10:30:00` 形式（时区 `Asia/Shanghai`）。
- 金额单位**均为分**（`Long`），如 `1399800` = 13998.00 元。

### 1.6 错误码速查

| HTTP | code | product-service | order-service |
| --- | --- | --- | --- |
| 400 | 40001 | 请求参数不合法 | 请求参数不合法 |
| 400 | 40002 | — | 支付回调签名校验失败 |
| 401 | 40101 | 未登录或登录已过期（缺 `X-User-Id` 头） | 未登录或登录已过期（缺 `X-User-Id` 头） |
| 403 | 40301 | 不是该商品的**创建者**（归属校验，见 `ProductOwnership`）；角色不足 | 没有操作权限（已预置，当前无接口触发） |
| 404 | 40401 | 商品不存在 | 订单不存在 |
| 404 | 40402 | SKU不存在 | 支付单不存在 |
| 404 | 40403 | 库存记录不存在 | 商品不存在 |
| 404 | 40404 | — | SKU不存在 |
| 409 | 40901 | 商品状态冲突 | 订单状态冲突 |
| 409 | 40902 | SKU状态冲突 | 商品状态不可购买 |
| 409 | 40903 | 可用库存不足 | SKU状态不可购买 |
| 409 | 40904 | 锁定库存不足 | 可用库存不足 |
| 409 | 40905 | — | 订单已超时 |
| 409 | 40906 | — | 支付金额与订单金额不一致 |
| 409 | 40907 | — | 支付单状态冲突（渠道不符等） |
| 409 | 40908 | — | 渠道流水号已被占用 |
| 409 | 40909 | — | 数据已存在，请勿重复提交（唯一索引冲突） |
| 500 | 50000 | 服务器内部错误 | 服务器内部错误 |
| 503 | 50001 | — | 远程服务调用失败（product-service 不可达） |

参数校验失败（`@Valid`）返回体形如：

```json
{ "code": 40001, "message": "name 商品名称不能为空", "data": null }
```

`message` 格式为 `字段名 + 空格 + 校验注解消息`，多个字段用 `"; "` 拼接；数组元素为 `items[0].quantity 购买数量至少为1`。

### 1.7 curl 写法约定

本文命令为 **Windows PowerShell + `curl.exe`** 写法。若本地 shell 把 JSON 里的双引号吞掉，改用文件体最稳：

```powershell
'{"name":"iPhone 17","productType":1}' | Set-Content -Encoding utf8 body.json
curl.exe -X POST http://localhost:8003/api/v1/products `
  -H "X-User-Id: u-1001" -H "Content-Type: application/json" --data-binary "@body.json"
```

## 2. product-service 接口清单

`{id}` 同时支持**内部主键**（纯数字，如 `1`）与**业务编号**（`P…` 商品 / `S…` SKU），由 `Identifiers` + `EntityLookup` 统一解析。

| # | 接口 | 方法 | 路径 | 经网关是否需要 JWT | 归属要求 |
| --- | --- | --- | --- | --- | --- |
| P1 | 创建商品 | POST | `/api/v1/products` | 是 | 登录（创建者 = `X-User-Id`） |
| P2 | 商品详情 | GET | `/api/v1/products/{id}` | **否**（白名单） | 公开 |
| P3 | 修改商品 | PUT | `/api/v1/products/{id}` | 是 | **仅创建者** |
| P4 | 删除商品 | DELETE | `/api/v1/products/{id}` | 是 | **仅创建者** |
| P5 | 上架 | POST | `/api/v1/products/{id}/on-shelf` | 是 | **仅创建者** |
| P6 | 下架 | POST | `/api/v1/products/{id}/off-shelf` | 是 | **仅创建者** |
| P7 | 创建 SKU | POST | `/api/v1/products/{id}/skus` | 是 | **仅创建者** |
| P8 | SKU 详情 | GET | `/api/v1/skus/{id}` | **否**（白名单） | 公开 |
| P9 | 修改 SKU | PUT | `/api/v1/skus/{id}` | 是 | **仅创建者** |
| P10 | 删除 SKU | DELETE | `/api/v1/skus/{id}` | 是 | **仅创建者** |
| P11 | 当前价格查询 | GET | `/api/v1/skus/{id}/price` | 是（`*` 不匹配两段） | 公开 |
| P12 | 修改价格 | PUT | `/api/v1/skus/{id}/price` | 是 | **仅创建者** |
| P13 | 查询库存 | GET | `/api/v1/skus/{id}/stock` | 是（`*` 不匹配两段） | 公开 |
| P14 | 增加库存 | POST | `/api/v1/skus/{id}/stock/increase` | 是 | **仅创建者** |
| P15 | 库存预占 | POST | `/api/v1/skus/{id}/stock/reserve` | 是 | **仅创建者** |
| P16 | 库存释放 | POST | `/api/v1/skus/{id}/stock/release` | 是 | **仅创建者** |
| P17 | 确认扣减 | POST | `/api/v1/skus/{id}/stock/confirm` | 是 | **仅创建者** |

> “仅创建者” = `product.uid` 必须等于网关注入的 `X-User-Id`（SKU / 价格 / 库存按所属商品判断），
> 由 `com.example.product.support.ProductOwnership` 统一校验；他人调用一律 `403 / 40301`，
> `message` 为 `无权操作他人商品: P…`。角色不改变归属：即便是 `ADMIN` 也要是创建者才能写。
> Dubbo 侧的 `ProductRpcService` / `StockRpcService` 服务于订单链路、没有用户上下文，**不做归属校验**。

> 下面的 curl 一律走**直连** `http://localhost:8003`（product-service 不解析 JWT），便于单服务排障；
> 直连时写接口需自带 `-H "X-User-Id: u-1001"`（当前用户只从这个头取），
> 换成 `$BASE_GW` + `-H "Authorization: Bearer $TOKEN"` 即可验证网关链路（`X-User-Id` 由网关自动注入）。

### P1 创建商品

`POST /api/v1/products`

> 创建者**不在请求体里**：取网关注入的 `X-User-Id`（= JWT 的 `sub`；早期由请求体传入，现已废弃），
> 直连测试需自带 `-H "X-User-Id: u-1001"`，否则返回 `401 / 40101`；请求体里若出现 `uid` 会被直接忽略。

**请求体**

| 字段 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| `name` | string | 是 | 非空，≤128 |
| `description` | string | 否 | ≤500 |
| `coverUrl` | string | 否 | ≤512 |
| `productType` | int | 是 | `1`-实物 `2`-虚拟 |

```powershell
curl.exe -X POST http://localhost:8003/api/v1/products `
  -H "X-User-Id: u-1001" -H "Content-Type: application/json" `
  -d '{"name":"iPhone 17","description":"新品首发","coverUrl":"https://cdn.example.com/1.png","productType":1}'
```

**预期结果（HTTP 200）**：`data` 为商品详情，新建商品 `status = 0`（下架），`skus` 为空数组。

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "product": {
      "id": 1,
      "productId": "P2QP7K3M1",
      "uid": "u-1001",
      "name": "iPhone 17",
      "description": "新品首发",
      "coverUrl": "https://cdn.example.com/1.png",
      "productType": 1,
      "status": 0,
      "createdAt": "2026-09-22T10:00:00",
      "updatedAt": "2026-09-22T10:00:00"
    },
    "skus": []
  }
}
```

**失败场景**

| 用例 | 请求体关键差异 | 预期 |
| --- | --- | --- |
| 缺身份头 | 不传 `X-User-Id`（如直连未带） | 401 / `40101`，`message = "缺少用户身份信息，请通过网关登录后访问"` |
| 请求体里多传 `uid` | 加 `"uid": "forged-uid"` | 被忽略：200，`data.product.uid` 仍为头里的 `u-1001` |
| 缺名称 | 去掉 `name` | 400 / `40001`，`"name 商品名称不能为空"` |
| 商品类型非法 | `"productType": 3` | 400 / `40001`，`"非法的商品类型: 3（1-实物 2-虚拟）"` |
| 缺商品类型 | 去掉 `productType` | 400 / `40001`，`"productType 商品类型不能为空"` |
| 名称超长 | `name` 129 个字符 | 400 / `40001`，`"name 商品名称长度不能超过128"` |
| JSON 语法错误/请求体非 JSON | `-d 'not-json'` | **500 / `50000`**（product-service 未单独处理 `HttpMessageNotReadableException`，见 §6） |

### P2 商品详情

`GET /api/v1/products/{id}`

```powershell
curl.exe http://localhost:8003/api/v1/products/P2QP7K3M1
curl.exe http://localhost:8003/api/v1/products/1          # 内部主键同样可用
```

**预期结果（HTTP 200）**：结构与 P1 相同；`skus` 为该商品下**未删除**的 SKU 列表，且每个 SKU 带库存快照
（`availableStock` / `lockedStock`）。

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "product": { "id": 1, "productId": "P2QP7K3M1", "uid": "u-1001", "name": "iPhone 17", "productType": 1, "status": 1, "createdAt": "2026-09-22T10:00:00", "updatedAt": "2026-09-22T10:30:00" },
    "skus": [
      { "id": 1, "skuId": "S2QP9Z0L4", "productDbId": 1, "name": "256G 黑色", "price": 1399800, "status": 1,
        "availableStock": 10, "lockedStock": 0, "createdAt": "2026-09-22T10:05:00", "updatedAt": "2026-09-22T10:05:00" }
    ]
  }
}
```

**失败场景**

| 用例 | 预期 |
| --- | --- |
| `id` 不存在（如 `P-NOT-EXIST`） | 404 / `40401`，`"商品不存在: P-NOT-EXIST"` |
| 商品已被逻辑删除 | 404 / `40401`（同上，删除后按不存在处理） |

### P3 修改商品

`PUT /api/v1/products/{id}` —— 字段为 `null` 表示不修改，传空对象报错。

| 字段 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| `name` | string | 否 | ≤128，非空白 |
| `description` | string | 否 | ≤500 |
| `coverUrl` | string | 否 | ≤512 |
| `productType` | int | 否 | `1` / `2` |

```powershell
curl.exe -X PUT http://localhost:8003/api/v1/products/P2QP7K3M1 `
  -H "X-User-Id: u-1001" -H "Content-Type: application/json" `
  -d '{"name":"iPhone 17 Pro","description":"改款"}'
```

**预期结果（HTTP 200）**：返回更新后的完整商品详情（同 P2 结构），`name` / `description` 已变更、`updatedAt` 刷新。

**失败场景**

| 用例 | 预期 |
| --- | --- |
| **用他人 uid（`X-User-Id: u-9999`）** | **403 / `40301`**，`"无权操作他人商品: P2QP7K3M1"` |
| 空对象 `{}` | 400 / `40001`，`"没有需要更新的字段"` |
| `{"name":"   "}`（纯空格） | 400 / `40001`，`"商品名称不能为空"` |
| `{"productType":9}` | 400 / `40001`，`"非法的商品类型: 9（1-实物 2-虚拟）"` |
| 不存在的商品 | 404 / `40401` |

### P4 删除商品

`DELETE /api/v1/products/{id}` —— 逻辑删除，并级联逻辑删除其下 SKU。

```powershell
curl.exe -X DELETE http://localhost:8003/api/v1/products/P2QP7K3M1 -H "X-User-Id: u-1001"
```

**预期结果（HTTP 200）**：`data` 被省略（null）。

```json
{ "code": 0, "message": "success" }
```

**失败场景**

| 用例 | 预期 |
| --- | --- |
| **用他人 uid** | **403 / `40301`** |
| 商品处于上架状态 | 409 / `40901`，`"商品处于上架状态，请先下架再删除"` |
| 商品不存在 / 已删除 | 404 / `40401` |
| 已下架商品再次删除 | 404 / `40401`（已删除即不存在） |

### P5 上架

`POST /api/v1/products/{id}/on-shelf`（无请求体）


**预期结果（HTTP 200）**：返回商品详情，`product.status = 1`。

**失败场景**

| 用例 | 预期 |
| --- | --- |
| **用他人 uid** | **403 / `40301`** |
| 商品下没有启用中的 SKU | 409 / `40901`，`"商品下没有启用中的SKU，无法上架"` |
| 商品已是上架状态 | 409 / `40901`，`"商品已处于上架状态"` |

### P6 下架

`POST /api/v1/products/{id}/off-shelf`（无请求体）

```powershell
curl.exe -X POST http://localhost:8003/api/v1/products/P2QP7K3M1/off-shelf -H "X-User-Id: u-1001"
```

**预期结果（HTTP 200）**：`product.status = 0`。

### P7 创建 SKU

`POST /api/v1/products/{id}/skus` —— 创建 SKU 时同步落一条 1:1 的库存记录。

| 字段 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| `name` | string | 是 | 非空，≤128 |
| `price` | long | 是 | 单位**分**，`0 ≤ price ≤ 99999999999` |
| `initialStock` | int | 否 | ≥0，不传按 `0` 处理 |

```powershell
curl.exe -X POST http://localhost:8003/api/v1/products/P2QP7K3M1/skus `
  -H "X-User-Id: u-1001" -H "Content-Type: application/json" `
  -d '{"name":"256G 黑色","price":1399800,"initialStock":10}'
```

**预期结果（HTTP 200）**：`status = 1`（启用），`lockedStock = 0`。

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "id": 1,
    "skuId": "S2QP9Z0L4",
    "productDbId": 1,
    "name": "256G 黑色",
    "price": 1399800,
    "status": 1,
    "availableStock": 10,
    "lockedStock": 0,
    "createdAt": "2026-09-22T10:05:00",
    "updatedAt": "2026-09-22T10:05:00"
  }
}
```

**失败场景**

| 用例 | 预期 |
| --- | --- |

| --- | --- | --- |

| 2 | `reserve 2` | 108 / 2 |

| 用例 | 预期 |
| --- | --- |

| `release`/`confirm` 数量 > 锁定库存 | 409 / `40904`，`"锁定库存不足，当前锁定 0，本次需要释放 2"`（confirm 文案为「本次需要确认 2」） |
| SKU 不存在 | 404 / `40402` |

> **鉴权说明**：`/api/v1/orders/**` 全部需要 JWT。服务从网关注入的 `X-User-Id` 头（值 = JWT 的 `sub`）取当前用户，

### O6 支付渠道异步回调（重点：签名）

`POST /api/v1/payments/callback` —— 免 JWT，身份由支付单反查。

| 字段 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| `paymentId` | string | 是 | 非空，≤32（O5 返回的支付单号） |
| `transactionId` | string | 是 | 非空，≤128（渠道流水号，全局唯一） |
| `paymentChannel` | int | 是 | 必须与支付单渠道一致 |
| `tradeStatus` | enum | 是 | `SUCCESS` / `FAILED` |
| `amount` | long | 是 | ≥1，必须与支付单金额一致（单位分） |
| `sign` | string | 是 | 非空，≤128，小写十六进制 HMAC-SHA256 |

**签名算法**（`PaymentSigner`）：

```
canonical = "amount={amount}&paymentChannel={paymentChannel}&paymentId={paymentId}&tradeStatus={tradeStatus}&transactionId={transactionId}"
sign      = HMAC-SHA256(secret, canonical) 的十六进制小写（secret = order.payment.callback-secret，默认 order-service-callback-secret）
```

字段按**字段名升序**拼接，值为原始字面量；`tradeStatus` 用枚举名字符串。

```powershell
# 1) 计算签名
$secret = 'order-service-callback-secret'
$paymentId = 'P2QQ4B9N2'
$transactionId = 'WX-TEST-0001'
$paymentChannel = 1
$tradeStatus = 'SUCCESS'
$amount = 2599800

$canonical = "amount=$amount&paymentChannel=$paymentChannel&paymentId=$paymentId&tradeStatus=$tradeStatus&transactionId=$transactionId"
$hmac = New-Object System.Security.Cryptography.HMACSHA256
$hmac.Key = [Text.Encoding]::UTF8.GetBytes($secret)
$sign = [BitConverter]::ToString($hmac.ComputeHash([Text.Encoding]::UTF8.GetBytes($canonical))).Replace('-','').ToLower()
Write-Host "sign=$sign"

# 2) 发送回调（经网关，免 JWT）
curl.exe -X POST $BASE_GW/api/v1/payments/callback `
  -H "Content-Type: application/json" `
  -d ('{"paymentId":"' + $paymentId + '","transactionId":"' + $transactionId + '","paymentChannel":' + $paymentChannel + ',"tradeStatus":"' + $tradeStatus + '","amount":' + $amount + ',"sign":"' + $sign + '"}')
```

**预期结果（HTTP 200）**

```json
{ "code": 0, "message": "success" }
```

**副作用校验（关键断言点）**

1. `GET /api/v1/orders/{orderId}` → `status = 2`、`statusName = "已完成"`、`paidAt` 与 `completedAt` 有值
   （回调内会同步 `markPaid`，随后 `confirmStock` 成功即 `COMPLETED`）。
2. `GET :8003/api/v1/skus/{skuId}/stock` → 锁定库存减少 2（`confirm` = 真正消耗，可用库存不变）。
3. 数据库 `payment_record` 新增一条回调流水（`callback_status = 1`）。

**失败场景**

| 用例 | 预期 |
| --- | --- |
| `sign` 写错（或签名体字段顺序/值改动） | 400 / `40002`，`"支付回调签名校验失败: paymentId=P2QQ4B9N2"`，且**不写流水** |
| `paymentId` 不存在 | 404 / `40402`，`"支付单不存在: P-XXX"` |
| 渠道不符（支付单是 1，回调传 2） | 409 / `40907`，`"支付渠道与支付单不一致: 回调=2, 支付单=1"` |
| `amount` 与支付单不一致 | 409 / `40906`，`"回调金额与支付单金额不一致: 支付单=2599800, 回调=100"` |
| 同一 `transactionId` 用于另一张支付单 | 409 / `40908`，`"渠道流水号已被其它支付单占用: WX-TEST-0001"` |
| **重复回调**（同一 `transactionId` + 已支付支付单） | 200 成功并再写一条流水（幂等，供渠道停止重试） |
| `tradeStatus: "FAILED"` | 200 成功；支付单状态置为「支付失败」（`3`），订单保持待支付，用户可重新 `pay` |
| `tradeStatus` 传非法值（如 `"OK"`） | 400 / `40001`，`"请求体格式不正确"`（枚举反序列化失败） |
| 缺 `sign` | 400 / `40001`，`"sign 签名不能为空"` |

## 4. 端到端串联用例（商品 → 订单 → 支付 → 完成）

| 步骤 | 命令 | 预期 |
| --- | --- | --- |
| 1 | P1 创建商品（带 `X-User-Id: 1001`） | 200，`productId = P…`，`status = 0`，`uid = 1001` |
| 2 | P7 创建 SKU（`initialStock = 10`，`price = 1299900`，带 `X-User-Id: 1001`） | 200，`skuId = S…`，库存 `10 / 0` |
| 3 | P5 上架商品（带 `X-User-Id: 1001`） | 200，`product.status = 1` |
| 4 | P2 商品详情 | 200，`skus[0].availableStock = 10` |
| 5 | O1 下单 `quantity = 2`（带 `X-User-Id: 1001`） | 200，`status = 0`，`totalAmount = 2599800`，`expireAt ≈ now + 30min` |
| 6 | P13 查库存 | 200，`8 / 2` |
| 7 | O2 查询我的订单 `status=0` | 200，`total ≥ 1` |
| 8 | O5 创建支付单 `paymentChannel = 1` | 200，`paymentId = P…`，`amount = 2599800`，`statusName = 待支付` |
| 9 | O5 重复调用 | 200，`paymentId` 与第 8 步相同（幂等） |
| 10 | O6 发送成功回调（正确签名） | 200 `{code:0}` |
| 11 | O3 查订单详情 | 200，`status = 2`、`statusName = 已完成` |
| 12 | P13 查库存 | 200，`8 / 0`（锁定 2 被确认扣减，可用不再变化） |
| 13 | P10 删除 SKU | 409 / `40902`（商品在上架状态） |
| 14 | P6 下架商品 → P4 删除商品 | 200；随后 P2 查详情 → 404 / `40401` |

> 换用其它 uid 会得到 `403 / 40301`；步骤 5 的下单用户也需与 `X-User-Id: 1001` 一致，否则 O3 查不到该订单。

| HTTP / code | product-service 触发条件 | order-service 触发条件 |
| --- | --- | --- |
| 200 / 0 | 全部正常路径 | 全部正常路径（含幂等重复调用） |
| 400 / 40001 | 参数缺失/越界、非法商品类型、非法 SKU 状态、空更新体 | 参数缺失/越界、重复 SKU、非法订单状态、非法支付渠道 |

| 403 / 40301 | **用他人 uid 调 P3–P7、P9、P10、P12、P14–P17 写接口**（归属校验） | —（已预置错误码，当前无接口触发） |

## 6. 注意事项与已发现的差异

1. **网关白名单与真实路径不一致（会影响测试，特别是「免登录」用例）**
   `gateway.auth.permit-all` 里写的是 `/api/v1/auth/refresh`、`/api/v1/auth/register`，
   而 `AuthController` 实际路径是 `/api/v1/auth/token/refresh`、`/api/v1/auth/register/phone`、`/api/v1/auth/register/email`。
   → **只有 `POST /api/v1/auth/login` 真正免登录**；注册/刷新若经网关会被 JWT 拦截（直连 auth-service 正常）。
   本文档的 JWT 获取步骤因此统一使用 login。
2. **Ant `*` 只匹配单段**：`GET /api/v1/skus/*` 放行的是 `/skus/{id}`，**不放行** `/skus/{id}/price` 与 `/skus/{id}/stock`；
   `GET /api/v1/products/*` 也不放行 `/products/{id}/skus`（且该接口本就是 POST）。
   若产品要求「价格/库存对未登录用户公开」，需把白名单改成 `GET /api/v1/skus/**`。
3. **请求体解析失败的处理不一致**：order-service 对 `HttpMessageNotReadableException` 返回 `400/40001 请求体格式不正确`；
   product-service 未单独处理，会落到兜底返回 `500/50000`。
4. **price / stock 是「双写」语义，注意断言方向**：`reserve` 与 `confirm` 都会减少 `availableStock`
   （reserve 减少可用并增加锁定；confirm 只减少锁定）。判断「总库存」时应看 `availableStock + lockedStock`。
5. **下单/取消的库存动作不在同一事务**：创建订单时先落库再 RPC 预占；取消/超时释放发生在**事务提交之后**，
   断言库存变化前建议留极小等待或用重试查询。
6. **订单超时是异步的**：`expireAt` 过期后需要 `OrderTimeoutTask`（默认 60s 扫描一次）把订单置为已取消；
   测试「订单已超时」错误码时，可直接把库里 `expire_at` 改到过去时间后调用 `pay` 接口（不依赖定时任务）。
7. **限流**：网关全局 10000 QPS、按 IP 100 QPS。压测/循环脚本触发 `429` 属预期，可在压测时调大
   `GATEWAY_RATE_LIMIT_IP_REPLENISH_RATE`。
8. **回调验签开关**：`order.payment.callback-secret` 为空串时会**跳过验签**并打 WARN 日志；
   用例 A（签名错误 → 40002）必须在配置了密钥的环境执行（默认值即为非空）。
9. **身份只能来自网关注入的头**：`POST /api/v1/products` 的创建者取 `X-User-Id`（= JWT 的 `sub`），
   请求体里的 `uid` 已被废弃并会被忽略；直连端口时若不带头会返回 `401/40101`。
   注：Dubbo RPC 入口（`ProductRpcService` 等）仍不支持外部调用方身份，属设计取舍。
10. **网关不再下发非标准头 `uid`**：`X-User-Id` 是唯一约定（网关先清后写，白名单分支全部清除），
   `gateway.auth.jwt.user-id-claim` 配置项已删除，uid 固定取标准 claim `sub`。
   下游服务仍兼容读取 `uid`（兜底），但正式用例请一律使用 `X-User-Id`。
11. **product-service 写接口按「归属」鉴权（本次新增）**：商品 / SKU / 价格 / 库存的 12 个写接口
    （P3–P7、P9、P10、P12、P14–P17）都要求 `product.uid == X-User-Id`，否则 `403 / 40301`
    （`无权操作他人商品: P…`），由 `com.example.product.support.ProductOwnership` 统一校验。
    - 判定顺序：先解析资源（不存在 → `404`），再判归属（非创建者 → `403`），最后才执行变更。
    - SKU / 价格 / 库存的归属按其**所属商品**判断，不是 SKU 自身字段。
    - 只读接口（P2、P8、P11、P13）保持公开，他人商品也能查看。
    - 角色（`ADMIN`）**不能**绕过归属：写接口只认创建者。
    - Dubbo 侧（`ProductRpcService` / `StockRpcService`，供 order-service 交易链路调用）
      **不做归属校验**，因为 RPC 链路没有用户上下文。
12. **各服务的错误码与响应结构已统一**：`auth / user / product / order` 都有同构的
    `common.ErrorCode`（`code / message / httpStatus`）、`common.BizException`、
    `common.ApiResponse`（`{code,message,data}`）、`common.GlobalExceptionHandler`、`common.CurrentUser`。
    统一编号：`40001` 参数、`40101` 未认证、`40301` 无权限、`404xx` 不存在、`409xx` 冲突、
    `42901` 限流、`50000` 内部错误。注意由此带来的两处对外变化：
    - user-service 的成功响应从「裸 `UserResponse`」变为 `{"code":0,"message":"success","data":{...}}`，
      注销从 `204 No Content` 变为 `200` + `{"code":0,"message":"success"}`。
    - auth-service 的业务码由 `1001 / 1002 / 1003` 改为 `40000`（通用业务失败）/`40001`（参数）/`42901`（限流），
      限流响应由 `400` 改为 `429 Too Many Requests`；401/403 的 `code` 由 `401 / 403` 改为 `40101 / 40301`。
