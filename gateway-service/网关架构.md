# 网关架构设计（gateway-service）

> 本文描述网关在平台中的位置、内部分层，以及路由、鉴权、限流、黑名单、日志五大能力的协作关系。
> 实现细节与配置清单见 [技术文档.md](技术文档.md)。


> **两条转发路径**：Java 侧走 `lb://`（Nacos 服务发现 + LoadBalancer 选实例），Go 侧走直连 `uri`（`VIDEO_SERVICE_URI` / `LIVE_SERVICE_URI` / `DANMAKU_SERVICE_URI`，默认 `http://localhost:900X`）。
> 原因是 Go 三服务**没有引入注册中心客户端**，Nacos 里查不到实例；但**鉴权链路完全共用**——两者都经 `JwtAuthenticationFilter` 注入 `X-User-Id` / `X-User-Role`，后端都不解析 JWT。

## 2. 外层网关定位

外层：**Spring Cloud Gateway + Spring Cloud Nacos**，优化的是**对外入口和流量治理**

> Auth-Service 负责 JWT 生成与生命周期管理，外层网关只涉及 JWT 统一鉴权和黑名单
>
> 登录接口的次数限流和外层网关限流：外层网关只对 IP 限流，登录接口包括 IP:UID

### 2.1 能力分层

```text
                    Gateway
                       │
       ┌───────────────┼────────────────┐
       │               │                │
       ▼               ▼                ▼
     路由             鉴权             限流
       │               │                │
       ├───────────────┼────────────────┤
       │               │                │
       ▼               ▼                ▼
     灰度             黑白名单          日志
```

- 所有 HTTP 请求统一从网关进入
- 统一做鉴权、限流、路由、灰度、日志、黑白名单
- 对外暴露一个稳定入口，后端服务可以自由拆分和替换
- 前端只认网关，不直接感知内部服务地址

### 2.2 能力与实现映射

| 能力 | 状态 | 实现载体 | 说明 |
| --- | --- | --- | --- |
| 路由 | 已落地 | `application.yml` 路由表 + Nacos + LoadBalancer | Java 五服务用 `lb://` 协议按服务名负载均衡（隐式路由已关闭）；Go 三服务用直连 `uri`，因未接入 Nacos |
| 鉴权 | 已落地 | `JwtAuthenticationFilter` | 验签 + `iss`/`aud`/`exp` 校验 + 身份头注入；`/ws/danmaku` 额外支持查询参数令牌（浏览器 WebSocket 无法设置请求头） |
| 限流 | 已落地 | `GlobalRateLimitFilter`、`IpRateLimitFilter` | Redis Lua 令牌桶，两级限流，Redis 异常时 fail-open |
| 黑名单 | 已落地 | `RedisBlacklistService` | 按 JWT `jti` 判定，key 为 `auth:blacklist:{jti}` |
| 日志 | 已落地 | `RequestIdLoggingFilter` + `logback-spring.xml` | `X-Request-Id` 全链路透传，访问日志含耗时与路由 |
| 灰度 | 规划中 | 路由权重 / Nacos 元数据 | 按请求头或用户标签分流 |
| 黑白名单（IP） | 规划中 | 网关过滤器 | 与 token 黑名单形成互补 |

### 2.3 请求处理流水线

```mermaid
sequenceDiagram
    autonumber
    participant C as Client
    participant GL as 全局限流
    participant IL as IP 限流
    participant RQ as 链路 ID / 日志
    participant AU as JWT 鉴权 + 黑名单
    participant S as Downstream Service

    C->>GL: HTTP 请求
    GL->>GL: Redis Lua 令牌桶
    GL-->>C: 429（令牌耗尽，流程终止）
    GL->>IL: 令牌充足
    IL->>IL: 按客户端 IP 扣减令牌
    IL-->>C: 429（令牌耗尽，流程终止）
    IL->>RQ: 令牌充足
    RQ->>RQ: 复用或生成 X-Request-Id
    RQ->>AU: 请求已带链路 ID
    AU-->>C: 401（验签 / 过期 / 黑名单失败）
    AU->>S: 注入 X-User-Id、X-User-Role 后转发
    S-->>C: 业务响应
    RQ->>RQ: 请求结束输出访问日志（status / latency / route）
```

**WebSocket 长连接的差异**：`/ws/danmaku` 进来时客户端只能用 `?access_token=<JWT>` 传令牌（浏览器 `new WebSocket(url)` 不能设请求头）。
网关取到令牌后**走完全相同的校验链路**，通过后同样注入身份头，并在转发前把 `access_token` 从 URL 上摘掉；Go 侧 `ws.go` **优先读 header**，查询参数 `uid` 只在 header 缺失时兜底，因此 `?uid=` 伪造身份无效。

```mermaid
sequenceDiagram
    autonumber
    participant C as Client（浏览器）
    participant G as Gateway :8000
    participant D as danmaku-service-go :9003

    C->>G: GET /ws/danmaku?roomId=5001&access_token=JWT（Upgrade: websocket）
    G->>G: 白名单未命中 → 从查询参数取令牌 → 验签 / iss / aud / exp / jti 黑名单
    G-->>C: 401（令牌无效）
    G->>D: GET /ws/danmaku?roomId=5001（access_token 已摘除）<br/>X-User-Id: u-2001 · X-User-Role: user
    D-->>C: 101 Switching Protocols，双向弹幕帧
```

## 3. 内部服务调用

内部：**Dubbo + Nacos**，优化的是**服务内部调用效率和服务发现**

```text
                         Nacos
                    ┌──────┴──────┐
                    │             │
              Spring Cloud      Dubbo
               Discovery       Service Discovery
                    │             │
                    ▼             ▼
                HTTP调用        RPC调用
                    │             │
                 Gateway       Service
```

- 服务之间走 RPC，不走 HTTP，调用更轻、更快
- 支持长连接、序列化、超时、重试、负载均衡
- 适合内部高频调用，比如 user-service 调用其他内部服务
- Nacos 负责注册发现，让 Dubbo 知道实例在哪

**边界划分：**

| 维度 | 外层（Gateway） | 内部（Dubbo） |
| --- | --- | --- |
| 协议 | HTTP/HTTPS | Dubbo RPC |
| 入口 | 唯一对外入口 `:8000` | 不对外暴露，仅注册到 Nacos |
| 治理重点 | 鉴权、限流、路由、日志 | 负载均衡、超时、重试、序列化 |
| 身份传递 | 网关注入 `X-User-Id` / `X-User-Role`（uid 取 JWT 标准 claim `sub`） | 通过 Dubbo 上下文隐式透传 |
| 服务发现 | Spring Cloud Discovery | Dubbo Service Discovery |

## 4. 部署与依赖形态

```mermaid
flowchart TB
    subgraph Edge[接入层]
        LB[SLB / Nginx] --> G1[gateway-service 实例 1]
        LB --> G2[gateway-service 实例 2]
    end

    subgraph Infra[基础设施]
        N[(Nacos<br/>注册 + 配置)]
        R[(Redis<br/>限流计数 + 黑名单)]
    end

    subgraph Services[业务服务]
        A[auth-service]
        U[user-service]
        V[video-service-go :9001]
        L[live-service-go :9002]
        D[danmaku-service-go :9003]
    end

    G1 -.注册/拉取.-> N
    G2 -.注册/拉取.-> N
    G1 --> R
    G2 --> R
    G1 -->|lb://| A
    G1 -->|lb://| U
    G2 -->|lb://| A
    G2 -->|lb://| U
    G1 ==>|"直连 uri（不在 Nacos）"| V
    G1 ==>|"直连 uri（不在 Nacos）"| L
    G1 ==>|"直连 uri（不在 Nacos）"| D
    G2 ==>|"直连 uri（不在 Nacos）"| V
    G2 ==>|"直连 uri（不在 Nacos）"| L
    G2 ==>|"直连 uri（不在 Nacos）"| D
```

要点：

- 网关本身**无状态**，可直接水平扩容；限流与黑名单状态集中在 Redis，多实例间天然共享配额。
- Redis 不可用时限流**放行**（fail-open），优先保证可用性；黑名单查询失败会向上抛出，需结合业务容忍度评估。
- 网关通过 Nacos 同时承担**服务发现**与**配置下发**（路由、限流参数可动态调整）。
- **Go 服务不在 Nacos 中**：其地址由 `VIDEO_SERVICE_URI` / `LIVE_SERVICE_URI` / `DANMAKU_SERVICE_URI` 环境变量给出，容器部署时改成 K8s Service DNS 名即可，网关配置无需改动。

## 5. 架构约束

1. **不可引入 `spring-boot-starter-web`**：网关基于 WebFlux，引入 Servlet 栈会导致启动失败；同理避免在过滤器中使用任何阻塞式调用。
2. **网关是唯一入口**：身份头（`X-User-Id` / `X-User-Role`，值来自 JWT 的 `sub` / `role`）的可信性完全依赖该前提，
   需通过网络策略保证后端服务不可被直连（网关只下发这两个头，客户端伪造的同名头会被先清后写）。
3. **鉴权只做校验不做签发**：JWT 生命周期由 `auth-service` 独占，网关仅持有验签密钥。
4. **敏感头隔离**：默认过滤器移除 `Cookie` / `Set-Cookie`，下游不应依赖浏览器凭证。
5. **链路 ID 必须贯穿**：任何新增过滤器都应保留 `X-Request-Id`，不得覆盖为新的值。
6. **白名单必须与下游真实路由逐条对齐**：白名单是纯字符串匹配，写错不报错、只会静默 401。当前按「方法 + 路径」声明，
   并用 `GatewayGoRoutingTests` 直接读取 `application.yml` 做回归断言（含反射比对 `AuthController` 映射）。
7. **令牌传递方式分层**：普通接口只认 `Authorization` 头；仅 `gateway.auth.jwt.token-query-paths` 中列出的路径（当前只有 `/ws/danmaku`）允许 `?access_token=`，且转发前必须摘除。

## 6. 演进方向

| 阶段 | 目标 | 关键动作 |
| --- | --- | --- |
| 近期 | 稳定性补齐 | 修复过滤器顺序冲突、访问日志改用 Logger、`X-Request-Id` 回写响应头 |
| 近期 | 配置动态化 | 路由与限流参数迁移到 Nacos 配置中心 |
| 中期 | 精细化限流 | 登录接口按 `IP:UID` 维度限流；路由级差异化配额 |
| 中期 | 灰度发布 | 路由权重 + Nacos 元数据标签路由 |
| 中期 | Go 服务注册中心化 | 给 Go 三服务补 Nacos 注册客户端，路由由直连 `uri` 换成 `lb://`，纳入统一负载均衡 |
| 中期 | 准入控制 | IP / 设备维度黑白名单 |
| 远期 | 可观测体系 | Prometheus 指标 + OpenTelemetry/Jaeger 全链路追踪 + JSON 日志采集 |
