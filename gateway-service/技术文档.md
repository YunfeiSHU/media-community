## 目标

实现请求链路统一透传：

Request -> Gateway -> X-Request-Id -> Service

同时在网关侧记录以下字段：

- requestId
- path
- method
- status
- latency
- route

## 设计说明

### 1. 请求 ID 生成与透传

网关在进入请求处理链时执行全局过滤器：

- 如果请求头已经携带 `X-Request-Id`，则直接复用
- 如果没有携带，则由网关生成 UUID 作为 `X-Request-Id`
- 该请求头会继续被写入转发请求，下游 Service 可直接读取

这样可以保证一次请求在 Gateway 和下游服务之间拥有同一个稳定标识。

### 2. 日志字段

网关在请求结束时记录访问日志，字段含义如下：

- `requestId`：请求链路唯一标识，对应 `X-Request-Id`
- `path`：原始请求路径
- `method`：HTTP 方法
- `status`：响应状态码
- `latency`：网关处理耗时，单位毫秒
- `route`：命中的网关路由标识

### 3. 过滤器顺序

请求 ID 过滤器使用较高优先级，保证：

1. 先补齐 `X-Request-Id`
2. 再进入鉴权和其他业务过滤器
3. 最终转发到下游服务

鉴权过滤器会保留并透传 `X-Request-Id`，同时继续注入用户信息头。

### 关键行为

- 统一生成或复用 `X-Request-Id`
- 将 `X-Request-Id` 写回转发请求头
- 请求完成后输出结构化日志
- 通过 MDC 将字段写入日志 pattern，便于后续接入日志采集系统

## 下游服务接入建议

下游 Service 只需要读取请求头中的 `X-Request-Id` 即可实现链路串联。

推荐下游也将该字段写入自己的日志上下文，这样可以在整条链路中按同一个 requestId 检索。

## 验证方式

1. 通过网关发送请求，不携带 `X-Request-Id`
2. 确认网关响应和下游服务都能看到同一个 `X-Request-Id`
3. 检查网关日志是否输出 requestId、path、method、status、latency、route

## 备注

- 当前实现使用网关访问日志输出链路字段，后续可替换为 Logback JSON appender、OpenTelemetry 或 ELK 结构化采集
- 如果需要把 `X-Request-Id` 同时写入响应头，也可以在过滤器中继续补充
