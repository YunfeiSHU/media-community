# user-service 技术方案

## 1. 职责与边界

### 1.1 负责什么

- 用户基础资料的创建、单个/批量查询、修改；
- 用户状态管理：`NORMAL` / `DISABLED` / `FROZEN` / `DELETED`，注销走逻辑删除；
- 通过 Dubbo `UserDubboService` 向 `auth-service` 提供创建、查询、存在性判断；
- 管理端按内部主键查询用户、修改用户状态。

### 1.2 不负责什么

| 能力 | 归属 | 边界 |
| --- | --- | --- |
| 密码、密码哈希、登录、Token、Refresh Token、验证码 | `auth-service` | `user` 表不含任何认证字段 |
| 账号状态（`account.status`） | `auth-service` | 与本服务的 `user.status` 是两套独立状态，互不联动 |
| JWT 校验 | `gateway-service` | 本服务不解析 JWT，只读网关注入的身份头 |

两个服务共用库 `auth_service`，通过业务标识 `uid`（`VARCHAR(32)`）关联，**不共享事务**。

### 1.3 技术栈与端口

| 项 | 值 | 说明 |
| --- | --- | --- |
| 语言 / 框架 | Java 17、Spring Boot 3.4.5 | Spring MVC + Spring Validation |
| 数据访问 | MyBatis 3.0.4，注解式 SQL 无 XML | `map-underscore-to-camel-case: true` |
| RPC | Dubbo 3.3.0 + Nacos 2.3.0 | `@DubboService` / `@DubboReference` |
| HTTP 端口 | `8001`（`SERVER_PORT`） | 网关侧路由 `lb://user-service` |
| Dubbo 协议端口 | `DUBBO_PROTOCOL_PORT`，默认 `-1`（随机） | Provider 注册到 Nacos，消费方按服务名发现，不依赖固定端口 |
| MySQL | `localhost:3306`，库 `auth_service` | `MYSQL_URL` / `MYSQL_USERNAME` / `MYSQL_PASSWORD` 覆盖 |
| 注册中心 | `nacos://localhost:8848` | `NACOS_REGISTRY_ADDRESS` / `NACOS_SERVER_ADDR` |
| 测试 | H2 内存库 + MockMvc | `application-test.yml` 中 Dubbo `registry.address: N/A`、`protocol.port: -1` |

配置见 `src/main/resources/application.yml`；服务一览、启动命令见 [`../README.md`](../README.md) §2 / §4。

## 2. 架构与身份来源

```text
客户端
  |
  v
gateway-service :8000
  |  校验 JWT；先清后写 X-User-Id / X-User-Role
  v
user-service :8001
  |
  +--> UserController ---------+
  |                            +--> UserService --> UserRepository --> MySQL auth_service.`user`
  +--> UserDubboServiceImpl ---+

auth-service :8002 -- Dubbo / Nacos --> UserDubboServiceImpl
```

| 层 | 主要职责 | 代码位置 |
| --- | --- | --- |
| Controller | REST 路由、`@Valid` 校验、身份头读取 | `controller/UserController.java` |
| RPC Provider | Dubbo 接口暴露、协议参数转换 | `rpc/UserDubboServiceImpl.java` |
| Service | 业务规则、状态变更、本地事务边界 | `service/UserService.java` |
| Repository | MyBatis SQL | `repository/UserRepository.java` |
| Entity / DTO | `User`、`UserStatus`、`UserRole`；请求/响应对象 | `entity/`、`dto/` |
| Common | `ErrorCode` / `BizException` / `ApiResponse` / `GlobalExceptionHandler` / `CurrentUser` | `common/` |

**身份只来自网关头**：

- `X-User-Id` = JWT 标准 claim `sub` = 用户业务标识 `uid`（**不是**自增主键 `id`）；
- `X-User-Role` = JWT 的 `role` claim（`ADMIN` / `user`），由 `CurrentUser.role()` 统一读取；
- 服务不解析 JWT，不采信请求体、查询参数或其它头里自报的用户标识与角色；早期网关注入的非标准 `uid` 头已废弃，**本服务也不再读取**——否则客户端自造一个头就能冒充任意用户（`common/CurrentUser.java:12`）；
- `CurrentUser.uid()` 缺头抛 `BizException(UNAUTHORIZED)` → HTTP 401 / `40101`；`requireAdmin()` 缺头同样是 401，角色不是 `ADMIN` 抛 `FORBIDDEN` → 403 / `40301`，比较忽略大小写（`common/CurrentUser.java:37`）；
- 该约定的前提是“请求确实来自网关”：绕过网关直连 `8001` 仍可伪造这两个头，生产环境必须在网络层禁止直连。

## 3. 数据模型

核心表 `user`（`src/main/resources/schema.sql`，`spring.sql.init.mode: always` 启动执行，`CREATE TABLE IF NOT EXISTS` 幂等，不清数据）：

```sql
CREATE TABLE IF NOT EXISTS `user` (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    uid VARCHAR(32) NOT NULL UNIQUE,
    nickname VARCHAR(64),
    avatar VARCHAR(512),
    gender VARCHAR(16),
    bio VARCHAR(500),
    role TINYINT NOT NULL DEFAULT 1,
    status TINYINT NOT NULL DEFAULT 1,
    created_at TIMESTAMP NOT NULL,
    updated_at TIMESTAMP NOT NULL
);
```

| 字段 | 说明 |
| --- | --- |
| `id` | 服务内部自增主键，只在管理端接口与库内使用，不对外作为身份 |
| `uid` | 跨服务稳定业务标识，`UUID.randomUUID()` 去掉横线后的 32 位十六进制，唯一索引 |
| `gender` | 字符串（`MALE` / `FEMALE` / `OTHER`），故 `VARCHAR(16)`；早期设计的 `TINYINT` 与对客契约冲突 |
| `bio` | `VARCHAR(500)`，与 `@Size(max = 500)` 对齐；曾经建表 255 而 DTO 500，导致“校验通过、入库报错”的 500 |
| `role` | `0` = 管理员，`1` = 普通用户；真正的角色名 `ADMIN` / `user` 由 auth-service 签发 JWT 时按 code 映射 |
| `status` | `TINYINT`，枚举见下表 |

| 状态 | 入库值 | 含义 |
| --- | --- | --- |
| `NORMAL` | 1 | 正常（创建时默认） |
| `DISABLED` | 2 | 禁用 |
| `FROZEN` | 3 | 冻结 |
| `DELETED` | 4 | 逻辑删除 |

设计取舍：

- 对内用 `id`、对外用 `uid`：`uid` 由服务端生成，auth 侧拿到回值后写入 `account.uid`；跨服务只传业务编号，不传对方自增主键。
- `auth-service` 的 `account` 表侧：`uid VARCHAR(32) NOT NULL`，唯一键；早期设计用 `user_id BIGINT` 关联，已废弃。`account.username` 列保留但恒为 `NULL`（只支持手机号 / 邮箱注册），唯一索引留给将来的用户名登录。
- 不引入 Flyway / Liquibase，表结构靠幂等的 `schema.sql` 管理；小表、单库，不为 `status` 建无查询支撑的索引。

### 3.1 索引与写一致性

- `id` 主键支撑管理端按内部主键查询；`uid` 唯一索引支撑 `GET /users/me`、三个 Dubbo 方法以及跨服务关联。
- 不为 `status` 预先建索引：目前没有按状态扫描的查询，索引只会增加写开销。
- 不建外键：`account.uid` 与 `user.uid` 的关联跨服务，外键会把两个服务的部署与回滚绑死。
- 所有资料变更在一个本地事务里完成，`created_at` / `updated_at` 由服务端统一写入，不依赖数据库默认值。

## 4. 需求一：创建用户基础资料（仅 Dubbo）

### 4.1 为什么没有 HTTP 创建接口

创建档案必须发生在“账号注册成功”这个服务端流程里：验证码校验、联系方式查重、密码策略都在 `auth-service`。若开放 `POST /api/v1/users`，客户端就能绕过这些前置条件直接造出没有 `account` 的孤儿档案，`uid` 也无从与登录凭证绑定。因此只暴露内网 Dubbo：

```text
com.example.userservice.rpc.UserDubboService#createUser(CreateUserCommand) -> RpcUser
```

`UserService.create(UserCreateRequest)` 这个 DTO 入口保留了，但当前没有 Controller 调用它，只作为后续管理端接口的复用点（`service/UserService.java:69`）。

### 4.2 请求对象

`CreateUserCommand`（`rpc/CreateUserCommand.java`，`Serializable`，auth 侧持有同名副本）：

| 字段 | 类型 | 必填 | 约束 | 说明 |
| --- | --- | --- | --- | --- |
| nickname | String | 否 | ≤ 64 | 用户昵称 |
| avatar | String | 否 | ≤ 512 | 头像地址 |
| gender | String | 否 | ≤ 16 | 性别扩展字段 |
| bio | String | 否 | ≤ 500 | 个人简介 |

**契约里没有 `username`**：本系统登录凭证只有手机号 / 邮箱，没有“账号名”概念，`user` 表也没有该列，早期文档“username 由认证侧传入”与实现不符。

### 4.3 流程

1. `auth-service` 在注册事务里调用 `createUser`；注册阶段还没有昵称/头像，传的是**空命令**，只为拿到 `uid` 并落一条 `status = NORMAL` 的默认资料。
2. Provider 校验命令非空，转调 `UserService.createUser`（RPC 与内部入口共用同一份赋值逻辑，避免两边在 `role` / `status` 上走偏）。
3. Service 生成 32 位 `uid`，`role = 1`、`status = NORMAL`，同一时间戳写 `created_at` / `updated_at`。
4. Repository 插入，唯一键冲突转 `40901`。
5. 返回 `RpcUser`；auth 用返回值写 `account.uid`，随后用户通过 `PUT /api/v1/users/me` 补资料（此前昵称为空，前端需兜底展示）。

```text
auth-service.registerByContact（本地事务）
  +- Dubbo createUser(空命令) -> user-service.createUser
  |                                +- uid = UUID 去横线（32 hex）
  |                                +- INSERT `user`(role=1, status=1)
  |                                `- 返回 RpcUser{uid, role=1}
  +- INSERT account(uid, phone|email, password_hash)
  `- commit
```

两个实现细节：

- `role` **必须显式赋值**。`role TINYINT NOT NULL DEFAULT 1` 只在“不写该列”时生效，显式写 `NULL` 在 MySQL 严格模式下直接报 `Column 'role' cannot be null`（`service/UserService.java:46`）。
- 唯一键只有 `uid`（随机串），所以冲突码是 `40901 用户标识冲突`，文案不是“用户名已存在”。

### 4.4 响应对象

`RpcUser` 只有两个字段（`rpc/RpcUser.java`）：

```json
{
  "uid": "7f2b0f8c0e5f4c08a2b9d7e2a8f9c123",
  "role": 1
}
```

资料字段不随 RPC 返回：调用方（auth）只需要 `uid` 与 `role`，其余资料走 HTTP 查询，避免 RPC 契约随视图字段扩散。

## 5. 需求二：查询用户资料

### 5.1 查询当前用户 `GET /api/v1/users/me`

身份取自请求头 `X-User-Id`（= `uid`），接口不接受任何指定用户的参数，所以“只能查自己”是结构上成立的，而不是靠业务判断：

```http
GET /api/v1/users/me HTTP/1.1
Host: localhost:8001
X-User-Id: 7f2b0f8c0e5f4c08a2b9d7e2a8f9c123
```

成功响应 HTTP `200`：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "userId": 1,
    "uid": "7f2b0f8c0e5f4c08a2b9d7e2a8f9c123",
    "nickname": "张三",
    "avatar": "https://example.com/avatar.png",
    "gender": "MALE",
    "bio": "用户简介",
    "status": "NORMAL",
    "createdAt": "2026-09-20T12:00:00",
    "updatedAt": "2026-09-20T12:00:00"
  }
}
```

`data` 是 `UserResponse`：`userId` 是内部主键，`status` 序列化为枚举名。查不到抛 `40401`：

```json
{ "code": 40401, "message": "user not found: 7f2b...", "data": null }
```

两点语义容易误读：`GET /users/me` 在 `uid` 查不到时同样返回 `40401`（不是返回空对象）；接口只校验“有没有身份头”，不校验用户状态，`DELETED` 用户仍会拿到自己的资料。

### 5.2 管理员查询 `GET /api/v1/admin/users/{userId}`

路径里的 `userId` 是 `user.id`（自增主键），**不是** `uid`；只有管理端用内部主键，对客链路一律用 `uid`，避免内部主键泄露成业务标识。接口先 `CurrentUser.requireAdmin()`，再按 `id` 查，查不到同样 `40401`。

### 5.3 Dubbo 查询

```text
RpcUser           getUser(String uid)
List<RpcUser>     batchGetUsers(List<String> uids)
Map<String,Boolean> checkUserExists(List<String> uids)
```

| 方法 | 语义 | 边界 |
| --- | --- | --- |
| `getUser` | 按 `uid` 查单个，查不到抛 `40401` 业务异常 | 只认 `uid`，不认内部主键 |
| `batchGetUsers` | 一次 `uid IN (...)` 查询，返回匹配到的用户 | 入参 `null` / 空 → 空列表；未做条数上限与分批 |
| `checkUserExists` | 同样走一次 `IN` 查询，返回 `uid -> 是否存在` | 按入参顺序放进 `LinkedHashMap`；`null` / 空 → 空 Map |

`auth-service` 的登录与刷新都用 `getUser` 取 `uid` / `role`：`@DubboReference(check = false, timeout = 3000)`，启动不因提供者离线失败，调用异常由上层转 `50000`。

## 6. 需求三：修改当前用户资料 `PUT /api/v1/users/me`

请求对象 `UserUpdateRequest`，四个字段全部可选，`null` 表示**不修改**（也因此该接口无法把字段清空为 `NULL`）：

```json
{
  "nickname": "新昵称",
  "avatar": "https://example.com/new-avatar.png",
  "gender": "FEMALE",
  "bio": "更新后的个人简介"
}
```

上限与建表对齐：`nickname` 64、`avatar` 512、`gender` 16、`bio` 500；超长或 JSON 非法统一 `40001`，消息带字段名（如 `bio 长度不能超过 500`）。

流程：`X-User-Id` → `findByUid` 拿到实体（不存在 `40401`）→ 只覆盖非 `null` 字段 → 刷新 `updated_at` → 同事务 `UPDATE` → 返回最新 `UserResponse`。目标用户永远由身份头决定，请求体里的任何用户标识都会被忽略。

| 场景 | 行为 |
| --- | --- |
| 请求体 `{}` | 不修改任何字段，仍刷新 `updated_at` 并返回当前资料 |
| 字段显式传 `null` | 与“不传”等价，保持原值 |
| `uid` 不存在 | `40401`，不产生写操作 |
| 字段超长 | `40001`，消息形如 `bio 长度不能超过 500` |

响应与 §5.1 的查询结构完全同构，只是被修改字段与 `updatedAt` 变化；SQL 是一次 `UPDATE` 覆盖四个资料列 + `updated_at`（`repository/UserRepository.java:41`）。

## 7. 需求四：用户注销 `DELETE /api/v1/users/me`

```http
DELETE /api/v1/users/me HTTP/1.1
Host: localhost:8001
X-User-Id: 7f2b0f8c0e5f4c08a2b9d7e2a8f9c123
```

无需请求体。流程：读身份头 → 按 `uid` 查用户（不存在 `40401`）→ 事务内 `UPDATE user SET status = 4, updated_at = ?` → 返回 `200`：

```json
{ "code": 0, "message": "success", "data": null }
```

**为什么是逻辑删除而不是物理删除**：订单、视频、弹幕等历史数据都靠 `uid` 关联用户，物理删会留下悬空引用；保留行还能审计，并允许管理端用 `PATCH` 把状态改回 `NORMAL`。注销不触碰 `auth-service` 的 `account` 与 Refresh Token——两者不在同一事务里，只能靠上层补偿保证最终一致。

## 8. 需求五：管理员修改用户状态 `PATCH /api/v1/admin/users/{userId}/status`

权限：`X-User-Role: ADMIN`（缺失 → 401，非管理员 → 403）。`userId` 同样是内部主键。

```json
{ "status": "FROZEN" }
```

`UserStatusRequest` 是 `record(@NotNull UserStatus status)`。`status` 传枚举名（`NORMAL` / `DISABLED` / `FROZEN` / `DELETED`），非法值由 Jackson 在反序列化阶段失败，经 `HttpMessageNotReadableException` 归为 `40001`，**不是** 500。响应 `200`，`data` 为更新后的完整资料，`status` 与 `updatedAt` 已刷新。

流程：`requireAdmin()` → 反序列化请求体（非法枚举即 400）→ 按内部主键 `getRequired(userId)`（不存在 `40401`）→ 事务内更新 `status` 与 `updated_at` → 返回最新资料。注意这里**不校验目标用户当前状态**，任何状态都能被改成任何状态。

两个实现细节：

- 状态更新没有状态机：`DELETED` 可以被 `PATCH` 直接改回 `NORMAL`，也允许对已是 `DELETED` 的用户重复置为 `DELETED`。
- 写库的 `updated_at` 与响应里的 `updatedAt` 必须用**同一个** `LocalDateTime`：两次 `now()` 在 Windows 上粒度可达毫秒级，否则会出现“响应与库内时间对不上”（`service/UserService.java:119`）。

## 9. 统一响应与错误码

`ApiResponse<T>` 为 `{ code, message, data }`，成功时 `code = 0`、`message = "success"`。本服务没有开启 `non_null` 裁剪，所以无业务数据的成功响应会显式带 `"data": null`。异常经 `GlobalExceptionHandler` 统一映射：

| 场景 | HTTP | 错误码 | 来源 |
| --- | --- | --- | --- |
| 参数/请求体不合法（超长、JSON 语法、非法枚举） | 400 | `40001` | `MethodArgumentNotValidException` / `HttpMessageNotReadableException` |
| 缺 `X-User-Id` | 401 | `40101` | `CurrentUser.uid()` |
| 非 `ADMIN` 访问管理接口 | 403 | `40301` | `CurrentUser.requireAdmin()` |
| 用户不存在 | 404 | `40401` | `BizException(USER_NOT_FOUND)` |
| `uid` 唯一键冲突 | 409 | `40901` | `DuplicateKeyException` |
| 未显式声明的异常 | 500 | `50000` | `Exception` 兜底 |

要点：角色不足走的是 `BizException`，不经过 `IllegalArgumentException` 分支；`Exception` 兜底会把没单独处理的客户端错误变成假的服务端故障，所以每类请求错误都要有专门处理器。全仓错误码总表见 [`../README.md`](../README.md) §5.3。

公共类（与 auth / product / order 同构，便于网关和前端统一处理）：

| 类 | 职责 |
| --- | --- |
| `common.ErrorCode` | 业务错误码枚举：`code` / `message` / `httpStatus` |
| `common.BizException` | 业务异常，携带 `ErrorCode`，由全局处理器转 HTTP |
| `common.ApiResponse` | 统一响应 `{code, message, data}`，`success()` / `failure()` 两个构造入口 |
| `common.GlobalExceptionHandler` | 异常 → HTTP 响应映射，含请求体解析失败与兜底 |
| `common.CurrentUser` | 只从网关注入头解析 `uid` / 角色，并提供 `requireAdmin()` |

## 10. 缓存、一致性与已知缺口

**当前没有缓存**：`pom.xml` 无 Redis 依赖，所有读取都是一次主键/唯一索引查询，直接落 MySQL。若将来引入缓存，边界是：key `user:profile:{uid}`，事务提交后删除、TTL 加随机抖动、空值短缓存防穿透；缓存只能加速，`status` 与权限判断必须以 MySQL 为准。

**跨服务一致性**：本地事务只包住 `user` 表的一次写。`auth-service` 的注册事务把 Dubbo 调用包在里面，`account` 插入失败会留下没有账号的孤儿 `user` 行；注销与状态变更也不会通知 auth。这些都没有补偿任务、没有幂等键（曾经规划的 `registration_id` 与注册状态表未实现）。

| 已知缺口 | 说明 |
| --- | --- |
| 注销不阻断登录 | auth 登录只校验 `account.status`，不查 `user.status`；`DELETED` 用户仍能登录，也仍能 `GET` / `PUT /users/me`（读到的是 `DELETED` 状态的资料） |
| 无状态机 | `PATCH` 可在任意状态间跳转，含 `DELETED` → `NORMAL` |
| 无幂等键 | 注册超时重试可能生成第二条 `user` 行 |
| 批量查询无上限 | `IN` 列表过长会拖慢 SQL，未分批 |
| 无乐观锁 | 资料更新是“读-改-写”，并发请求后写覆盖先写 |

## 11. 构建、测试与部署

```powershell
mvn spring-boot:run   # :8001，启动时执行 schema.sql
mvn test              # H2 内存库 + MockMvc，不连本地 MySQL
```

启动依赖的环境变量（缺省值即本地开发配置）：

```text
SERVER_PORT=8001
MYSQL_URL=jdbc:mysql://localhost:3306/auth_service?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai&useSSL=false&allowPublicKeyRetrieval=true
MYSQL_USERNAME=root
MYSQL_PASSWORD=******
NACOS_SERVER_ADDR=localhost:8848
NACOS_REGISTRY_ADDRESS=nacos://localhost:8848
```

- 测试 profile：`@ActiveProfiles("test")` + `src/test/resources/application-test.yml`（H2 `MODE=MySQL`、Dubbo `registry.address: N/A`）。`UserControllerIntegrationTest` 覆盖：Dubbo 创建与查询、按 uid 读写当前用户、逻辑注销后仍可读、管理员按内部主键查询、角色只认网关头（403/401/200）、非法枚举与超长字段 `40001`、`40401`。
- 日志：`RequestIdFilter` 读取或生成 `X-Request-Id`，写入 MDC `requestId`（`common/http/RequestIdConstants.java:5`），便于串联一次请求的 Controller / SQL 日志。
- 部署：K8s 清单里只有 `user-service` 的 `Service`（HTTP 80 → `http`、Dubbo 20880 → `dubbo`），**没有对应 Deployment**，因此该 Service 目前没有后端端点；同一套清单里只有 `auth-service` 有 Deployment（2 副本），MySQL / Redis 用 `emptyDir`，仅用于本地演示。
- 生产前必须：网络层禁止直连 `8001`、由网关覆盖身份头；MySQL 密码与 Nacos 凭据通过环境变量 / Secret 注入，不提交 Git。测试通过只说明 H2 + MockMvc 链路正确，不代表生产库配置正确。
