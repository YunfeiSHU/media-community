# user-service 技术方案

## 1. 项目概述

### 1.1 服务目标

`user-service` 负责用户基础资料和用户状态管理，为 `auth-service` 及其他业务服务提供统一的用户资料查询能力。

### 1.2 业务边界

本服务负责：

- 创建用户基础资料
- 查询当前用户和指定用户资料
- 批量查询用户资料
- 修改当前用户资料
- 用户逻辑注销
- 管理员查询用户和修改用户状态
- 通过 Dubbo 提供用户查询、创建和存在性判断能力

本服务不负责：

- 密码保存与密码加密
- 登录、Token、Refresh Token
- 验证码和账号认证

以上认证能力由 `auth-service` 负责。两个服务通过用户业务标识 `uid` 关联，不共享业务代码中的数据库事务。

### 1.3 技术栈与运行端口

- Java 17+
- Spring Boot 3.4
- Spring MVC、Spring Validation
- MyBatis Spring Boot Starter
- Apache Dubbo 3.3
- MySQL 8+
- Maven
- 测试使用 H2 内存数据库和 MockMvc

当前运行配置：

| 类型 | 地址 | 说明 |
| --- | --- | --- |
| HTTP | `localhost:8082` | REST 接口 |
| Dubbo | `localhost:20881` | RPC Provider |
| MySQL | `localhost:3306/auth_service` | 通过环境变量覆盖 |

## 2. 总体架构

```text
客户端
  |
  v
Gateway/Auth-Service -- 注入 X-User-Id、X-User-Role --> user-service
                                                        |
                                                        v
                                              Controller / Dubbo Provider
                                                        |
                                                        v
                                                   UserService
                                                        |
                                                        v
                                                   MyBatis
                                                        |
                                                        v
                                                     MySQL
```

代码分层：

| 层 | 主要职责 |
| --- | --- |
| Controller | REST 路由、请求参数校验、身份头读取 |
| RPC Provider | Dubbo 接口暴露和 RPC 参数转换 |
| Service | 业务规则、状态变更和事务边界 |
| Repository | MyBatis SQL 和数据库访问 |
| Entity | 用户实体和用户状态枚举 |
| DTO | 请求对象、响应对象和 RPC 对象 |
| Exception | 业务异常到 HTTP 错误响应的统一转换 |

普通用户接口从 `X-User-Id` 获取当前用户，不接受客户端传入目标用户 ID。管理员接口必须校验 `X-User-Role: ADMIN`。生产环境必须由网关覆盖或清理客户端伪造的身份请求头。

## 3. 需求一：创建用户基础资料

### 3.1 接口

当前实现通过 Dubbo 提供：

```text
com.example.userservice.rpc.UserDubboService#createUser(CreateUserCommand)
```

该接口主要由 `auth-service` 在注册成功后调用。HTTP 层没有公开创建用户接口，避免客户端绕过认证服务直接创建账号资料。

### 3.2 请求文

请求对象：`CreateUserCommand`

| 字段 | 类型 | 必填 | 约束 | 说明 |
| --- | --- | --- | --- | --- |
| username | String | 是 | 不超过 64 个字符 | 账号唯一标识，由认证侧传入 |
| nickname | String | 是 | 不超过 64 个字符 | 用户昵称 |
| avatar | String | 否 | 不超过 512 个字符 | 头像地址 |
| gender | String | 否 | 不超过 16 个字符 | 性别扩展字段 |
| bio | String | 否 | 不超过 500 个字符 | 个人简介 |

示例：

```json
{
  "username": "zhangsan",
  "nickname": "张三",
  "avatar": "https://example.com/avatar.png",
  "gender": "MALE",
  "bio": "用户简介"
}
```

### 3.3 设计流程

1. `auth-service` 完成账号注册和认证字段校验。
2. `auth-service` 调用 `createUser`，只传递资料字段，不传递密码。
3. Provider 校验必要字段，并调用 `UserService`。
4. `UserService` 生成唯一 `uid`，设置状态为 `NORMAL`，写入创建时间和更新时间。
5. Repository 将用户资料写入 MySQL，数据库唯一约束负责防止重复数据。
6. 返回用户 RPC 响应；`auth-service` 使用返回的 `uid` 写入自己的账号表。
7. 跨服务调用不共享事务。若账号写入失败，应由上层补偿任务重试或调用逻辑注销流程。

生产环境建议增加 `registration_id` 幂等键和注册状态表，使超时重试返回原创建结果，而不是重复创建资料。

### 3.4 响应文

响应对象：`RpcUser`

```json
{
  "id": 1,
  "uid": "7f2b0f8c0e5f4c08a2b9d7e2a8f9c123",
  "username": "zhangsan",
  "nickname": "张三",
  "avatar": "https://example.com/avatar.png",
  "gender": "MALE",
  "bio": "用户简介",
  "status": "NORMAL",
  "createdAt": "2026-09-20T12:00:00",
  "updatedAt": "2026-09-20T12:00:00"
}
```

### 3.5 MySQL 设计思路

- 使用 `id` 作为服务内部自增主键，使用 `uid` 作为跨服务稳定业务标识。
- `uid` 建立唯一索引，确保用户资料不会出现重复业务标识。
- 初始状态写入 `NORMAL`。
- 创建操作使用本地事务；唯一键冲突转换为业务冲突错误。
- 密码、密码哈希和认证字段不进入 `user` 表。

## 4. 需求二：查询用户资料

### 4.1 REST 接口

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/api/v1/users/me` | `X-User-Id` | 查询当前登录用户资料 |
| GET | `/api/v1/admin/users/{userId}` | `X-User-Role: ADMIN` | 管理员按内部用户 ID 查询资料 |

### 4.2 请求文

查询当前用户：

```http
GET /api/v1/users/me HTTP/1.1
Host: localhost:8082
X-User-Id: 1
```

管理员查询：

```http
GET /api/v1/admin/users/1 HTTP/1.1
Host: localhost:8082
X-User-Role: ADMIN
```

### 4.3 设计流程

1. Controller 读取请求头并校验身份信息。
2. 管理员接口额外校验角色是否为 `ADMIN`。
3. Service 调用 Repository 按 `id` 查询用户。
4. 查询不到用户时抛出资源不存在异常。
5. 将 Entity 转换为 `UserResponse` 返回，避免直接暴露数据库对象。

### 4.4 响应文

成功响应 HTTP `200`：

```json
{
  "userId": 1,
  "username": "zhangsan",
  "nickname": "张三",
  "avatar": "https://example.com/avatar.png",
  "gender": "MALE",
  "bio": "用户简介",
  "status": "NORMAL",
  "createdAt": "2026-09-20T12:00:00",
  "updatedAt": "2026-09-20T12:00:00"
}
```

异常响应示例：

```json
{
  "code": "USER_NOT_FOUND",
  "message": "user not found: 1"
}
```

### 4.5 Dubbo 查询接口

`UserDubboService` 同时提供：

```text
getUser(String uid)
batchGetUsers(List<String> uids)
checkUserExists(List<String> uids)
```

查询类 RPC 只使用 `uid`，批量请求为空时直接返回空列表或空 Map。批量 SQL 使用 `IN` 查询，并按业务需要限制单次 UID 数量，避免 SQL 过长。

### 4.6 Redis 设计思路

当前项目未引入 Redis 依赖，查询默认直接访问 MySQL。访问量较大时可增加缓存：

- Key：`user:profile:{uid}`
- Value：用户资料 JSON
- TTL：建议 5 至 30 分钟，并增加随机抖动避免同时过期。
- 查询顺序：先查 Redis，未命中再查 MySQL，成功后回填 Redis。
- 修改、状态变更和注销成功后删除对应缓存，保证不会长期读取旧资料。
- 缓存只作为加速层，Redis 不可用时降级查询 MySQL。
- 对不存在的用户可设置较短的空值缓存，防止恶意请求造成缓存穿透。

## 5. 需求三：修改当前用户资料

### 5.1 接口

```http
PUT /api/v1/users/me
```

权限：必须携带有效的 `X-User-Id`。

### 5.2 请求文

请求对象：`UserUpdateRequest`。所有字段均可选，未传字段保持原值。

```json
{
  "nickname": "新昵称",
  "avatar": "https://example.com/new-avatar.png",
  "gender": "FEMALE",
  "bio": "更新后的个人简介"
}
```

字段长度限制：`nickname` 不超过 64，`avatar` 不超过 512，`gender` 不超过 16，`bio` 不超过 500。

### 5.3 设计流程

1. 从 `X-User-Id` 获取目标用户 ID，不使用请求体中的用户 ID。
2. 校验请求体字段长度和格式。
3. 查询用户，用户不存在则返回 404。
4. 仅更新请求中非空的字段，并刷新 `updated_at`。
5. 在本地事务中执行更新并返回最新对象。
6. 若使用 Redis，事务成功后删除 `user:profile:{uid}` 缓存。

### 5.4 响应文

成功响应 HTTP `200`，响应结构与查询资料一致：

```json
{
  "userId": 1,
  "username": "zhangsan",
  "nickname": "新昵称",
  "avatar": "https://example.com/new-avatar.png",
  "gender": "FEMALE",
  "bio": "更新后的个人简介",
  "status": "NORMAL",
  "createdAt": "2026-09-20T12:00:00",
  "updatedAt": "2026-09-20T12:10:00"
}
```

## 6. 需求四：用户注销

### 6.1 接口

```http
DELETE /api/v1/users/me
```

权限：必须携带有效的 `X-User-Id`。

### 6.2 请求文

该接口不需要请求体：

```http
DELETE /api/v1/users/me HTTP/1.1
Host: localhost:8082
X-User-Id: 1
```

### 6.3 设计流程

1. 从身份请求头获取当前用户 ID。
2. 查询用户并确认用户存在。
3. 在事务中将 `status` 更新为 `DELETED`，不物理删除记录。
4. 清理用户资料缓存。
5. 返回 HTTP `204 No Content`。
6. `auth-service` 应同步禁用账号登录能力；该跨服务动作通过事务消息或补偿任务保证最终一致。

### 6.4 响应文

成功响应：

```http
HTTP/1.1 204 No Content
```

逻辑删除保留用户记录，便于历史业务数据继续通过 `uid` 关联用户。

### 6.5 MySQL 与 Redis 设计思路

- MySQL 使用状态字段实现逻辑删除，禁止物理删除用户主记录。
- `DELETED` 用户不应再被认证服务签发有效登录态。
- 更新数据库成功后删除缓存，避免缓存继续返回 `NORMAL` 状态。
- 重要业务场景可发布 `UserDeleted` 事件，由订阅方清理自己的用户数据或权限关系。

## 7. 需求五：管理员管理用户状态

### 7.1 接口

```http
PATCH /api/v1/admin/users/{userId}/status
```

权限：必须携带 `X-User-Role: ADMIN`。

### 7.2 请求文

请求对象：`UserStatusRequest`。

```json
{
  "status": "FROZEN"
}
```

支持状态：

| 状态 | 含义 |
| --- | --- |
| NORMAL | 正常 |
| DISABLED | 禁用 |
| FROZEN | 冻结 |
| DELETED | 逻辑删除 |

### 7.3 设计流程

1. Controller 校验管理员角色。
2. 校验状态值是否为系统支持的枚举值。
3. Service 查询目标用户。
4. 在事务中更新 `status` 和 `updated_at`。
5. 清除用户资料缓存，并返回最新用户资料。
6. 认证服务或权限服务根据状态变化限制登录、访问或业务操作。

### 7.4 响应文

成功响应 HTTP `200`：

```json
{
  "userId": 1,
  "username": "zhangsan",
  "nickname": "张三",
  "avatar": "https://example.com/avatar.png",
  "gender": "MALE",
  "bio": "用户简介",
  "status": "FROZEN",
  "createdAt": "2026-09-20T12:00:00",
  "updatedAt": "2026-09-20T12:20:00"
}
```

## 8. MySQL 数据库设计

### 8.1 表结构

核心表为 `user`：

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT | PK, AUTO_INCREMENT | 服务内部主键 |
| uid | VARCHAR(32) | NOT NULL, UNIQUE | 对外稳定业务标识 |
| username | VARCHAR(64) | 按业务决定是否唯一 | 账号展示或关联字段 |
| nickname | VARCHAR(64) | 可空 | 用户昵称 |
| avatar | VARCHAR(512) | 可空 | 头像地址 |
| gender | VARCHAR/TINYINT | 可空 | 性别扩展字段 |
| bio | VARCHAR(500) | 可空 | 个人简介 |
| status | TINYINT | NOT NULL | 用户状态 |
| created_at | TIMESTAMP | NOT NULL | 创建时间 |
| updated_at | TIMESTAMP | NOT NULL | 修改时间 |

### 8.2 索引与一致性

- `id` 用于服务内部主键查询。
- `uid` 建立唯一索引，供 Dubbo 和跨服务关联查询。
- 按实际查询量为 `status`、`username` 增加索引，避免无效索引。
- 所有资料变更使用事务，时间字段由服务统一写入。
- 生产环境使用 Flyway 或 Liquibase 管理表结构版本，不依赖应用启动时反复执行初始化脚本。

### 8.3 配置

```text
MYSQL_URL=jdbc:mysql://localhost:3306/auth_service?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai&useSSL=false&allowPublicKeyRetrieval=true
MYSQL_USERNAME=root
MYSQL_PASSWORD=******
```

数据库密码不得提交到 Git。生产环境应通过环境变量、密钥管理服务或容器 Secret 注入。

## 9. Redis 总体设计思路

当前工程未引入 Redis，因此 Redis 是后续性能优化方案，不是启动必需依赖。

### 9.1 缓存内容

- 用户资料缓存：`user:profile:{uid}`
- 用户状态缓存：可包含在用户资料缓存中，避免重复 Key
- 空值缓存：`user:profile:empty:{uid}`，短 TTL

### 9.2 读写策略

- 读：Redis 命中直接返回；未命中查询 MySQL 后回填。
- 写：先提交 MySQL 事务，成功后删除缓存。
- 删除：注销和状态更新后删除缓存。
- 故障：Redis 超时或不可用时降级 MySQL，不影响核心业务可用性。
- 防护：设置 TTL、随机过期时间、空值缓存和单飞/分布式锁，降低缓存击穿风险。

### 9.3 一致性边界

Redis 只作为最终一致的查询缓存，不能作为用户资料唯一存储。用户状态、注销和权限相关判断必须以 MySQL 或认证服务的可靠状态为准，不能仅依赖客户端缓存。

## 10. 统一异常与响应

由 `GlobalExceptionHandler` 将业务异常转换为统一错误响应：

| 场景 | HTTP 状态码 |
| --- | --- |
| 请求参数错误或身份头非法 | 400 |
| 未登录或缺少身份头 | 400/401，按网关约定 |
| 非管理员操作管理员接口 | 403 |
| 用户不存在 | 404 |
| 用户资料或唯一标识冲突 | 409 |
| 未知系统异常 | 500 |

建议统一响应格式：

```json
{
  "code": "USER_NOT_FOUND",
  "message": "user not found",
  "timestamp": "2026-09-20T12:00:00"
}
```

## 11. 事务、补偿与部署注意事项

- 创建、修改资料、修改状态和注销均使用本地事务。
- user-service 与 auth-service 不共享数据库事务，通过幂等、重试、对账和补偿保证最终一致。
- Dubbo Provider 当前直连配置使用 `registry.address: N/A`，生产环境建议使用 Nacos 或 Zookeeper。
- 当前 HTTP 端口为 `8082`，Dubbo 端口为 `20881`；调用方必须使用相同的 Dubbo 端口。
- 启动前确认 MySQL 账号密码正确，并确认数据库已创建。
- 测试环境使用 H2，不依赖本地 MySQL；测试通过不代表生产数据库配置一定正确。
