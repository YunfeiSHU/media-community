# user-service 技术方案

## 1. 目标与边界

`user-service` 负责用户基础资料和用户状态，是其他业务服务判断用户当前状态的统一来源。

负责范围：

- 创建用户基础资料
- 查询当前用户、单个用户和批量用户
- 修改当前用户资料
- 查询和管理用户状态
- 用户逻辑注销
- 用户存在性查询

不负责：密码、密码加密、登录、Token、Refresh Token。这些能力由 `auth-service` 提供。

## 2. 技术栈

- Java 17+
- Spring Boot 3.4
- Spring MVC
- Spring Validation
- MyBatis Spring Boot Starter
- Apache Dubbo 3.3
- MySQL 8+
- Maven
- 测试使用 H2 内存数据库和 MockMvc，不依赖本地 MySQL

## 3. 分层结构

```text
com.example.userservice
├── controller       HTTP 接口和参数校验
├── service          业务规则和事务边界
├── repository       MyBatis 数据访问
├── entity           数据库实体和状态枚举
├── dto              请求、响应对象
├── exception        业务异常和统一异常响应
└── rpc              Dubbo 服务接口、DTO 和 Provider
```

请求链路：

```text
Gateway -> Controller -> Service -> Repository -> MySQL
              |
              +-> X-User-Id / X-User-Role
```

网关认证成功后传递 `X-User-Id`。普通用户资料变更只使用该身份 ID，不允许客户端通过请求体传入目标用户 ID。管理员状态操作要求 `X-User-Role: ADMIN`。

## 4. 数据模型

表名为 `user`，核心字段如下：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT | user-service 内部自增主键 |
| uid | VARCHAR(32) | 对外稳定业务标识，唯一，由 user-service 生成，并与 account.uid 共享 |
| nickname | VARCHAR(64) | 昵称 |
| avatar | VARCHAR(512) | 头像地址 |
| gender | TINYINT | 性别扩展字段 |
| bio | VARCHAR(255) | 个人简介 |
| status | TINYINT | `NORMAL`、`DISABLED`、`FROZEN`、`DELETED` |
| created_at | TIMESTAMP | 创建时间 |
| updated_at | TIMESTAMP | 修改时间 |

注销采用逻辑删除：只更新 `status = DELETED`，不物理删除用户记录，保证其他业务数据仍可通过业务 `uid` 关联原用户。

## 5. P0 接口

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/api/v1/users/me` | `X-User-Id` | 查询当前用户完整资料 |
| PUT | `/api/v1/users/me` | `X-User-Id` | 修改当前用户资料 |
| DELETE | `/api/v1/users/me` | `X-User-Id` | 当前用户逻辑注销 |
| GET | `/api/v1/admin/users/{id}` | `X-User-Role: ADMIN` | 管理员查询用户 |
| PATCH | `/api/v1/admin/users/{id}/status` | `X-User-Role: ADMIN` | 管理员修改用户状态 |

Dubbo 服务接口为 `com.example.userservice.rpc.UserDubboService`，默认监听 `20880`，提供：

```text
createUser
getUser
batchGetUsers
checkUserExists
```

创建、单查、批量查询和存在性判断均通过 Dubbo 提供。Provider 使用 `@DubboService` 暴露，业务逻辑复用 `UserService`。本地配置 `registry.address: N/A` 使用直连；生产环境应配置 Nacos 或 Zookeeper，并将 RPC 接口 DTO 抽取到独立 API 模块供消费者依赖。

`CreateUserCommand` 携带 `registrationId` 和资料字段（`nickname`、`avatar`、`gender`、`bio`）；认证联系方式和密码不进入 user-service。`createUser` 以 `registrationId` 作为幂等键：首次请求由 user-service 生成 32 位 `uid`，初始化用户状态为 `NORMAL`，写入 `user` 表并返回 `uid`；相同 `registrationId` 的重试直接返回原创建结果，不得再次生成资料。auth-service 使用返回的 `uid` 写入自己的 `account.uid` 和认证字段。

### 5.1 RPC 调用与补偿流程

user-service 只负责用户资料这一侧的事务，不与 auth-service 共享数据库事务。Provider 按以下规则处理注册 RPC：

1. 校验 `registrationId` 和资料参数；缺失或格式非法时立即返回参数错误，不执行写入。
2. 先查询幂等记录。已完成的请求直接返回原 `uid`；处理中请求返回可重试状态；不存在的请求才创建用户资料并记录 `registrationId -> uid`。
3. 用户资料写入和幂等记录必须在同一个本地事务中完成，唯一约束保证并发请求不会创建两条资料。
4. 返回结果包含 `uid`、处理状态和必要的错误码，Provider 不返回 user-service 内部自增 `id`。
5. auth-service account 写入失败时，由对账任务重试；确认注册失败后调用补偿接口，将该资料逻辑删除。补偿接口也必须按 `registrationId` 幂等。
6. 查询类 RPC 只接受 `uid`，批量接口对空列表返回空结果；网络超时由调用方有限重试，Provider 不自行重复执行非幂等操作。

建议的扩展接口为：

```text
createUser(CreateUserCommand command)
getRegistration(String registrationId)
cancelRegistration(String registrationId)
```

其中 `getRegistration` 用于 auth-service 超时后的结果确认，`cancelRegistration` 用于最终失败后的逻辑补偿。注册状态建议包含 `PROCESSING`、`COMPLETED`、`CANCELLED`，禁止通过“重新调用 createUser”来判断上一次请求是否成功。

当前直连配置：

```yaml
dubbo:
    registry:
        address: N/A
    protocol:
        name: dubbo
        port: 20880
```

## 6. 异常处理

异常统一放在 `exception` 包，由 `GlobalExceptionHandler` 转换为 `ApiError`：

- 用户不存在：HTTP 404
- 用户资料或 uid 冲突：HTTP 409
- 参数错误、缺少或非法 `X-User-Id`：HTTP 400
- 非管理员执行状态管理：HTTP 403

## 7. 数据库与配置

生产默认连接 MySQL，可通过环境变量覆盖：

```text
MYSQL_URL=jdbc:mysql://localhost:3306/user_service?... 
MYSQL_USERNAME=root
MYSQL_PASSWORD=******
```

启动前创建数据库：

```sql
CREATE DATABASE user_service DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

`schema.sql` 和 `data.sql` 负责初始化表结构及演示用户。生产环境建议使用 Flyway/Liquibase 管理版本化迁移，并由网关覆盖客户端伪造的内部请求头。

## 8. 事务与一致性

- 创建、修改资料、修改状态、注销使用事务。
- 状态修改通过单条更新语句完成，并同步返回最新状态。
- P0 暂不实现用户变更事件；后续可基于事务消息或 Outbox 发布昵称、头像、状态变化事件。
